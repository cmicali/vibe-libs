# audio/Decode

One opened audio file, read as PCM. It holds `AudioFileHandle`, the file handle, with its MPEG and stream decodes and its read-ahead seam. It came from Vibe. It depends on `core/Common`, on `files/FileLoading` for a stream's and a read-ahead's bytes, and on the five decoders it hosts: `third_party/dr_mp3`, `dr_flac`, `dr_wav`, `vorbis`, and `wavpack`. Its surface is `AVAudioFile`'s: the file's facts, a cursor in file frames, and reads into a PCM buffer. It also writes, through an `ExtAudioFile`, so an app's converter and its test fixtures share the class. It reads no app's settings, strings, or types.

`audio/Player`, `waveform/WaveformLoading`'s loader, and `media/Metadata`'s CoreAudio fallback each open one, and so may an app's own code. What a player does with a handle, its voices, its fades, and its deadline, is `audio/Player/AGENTS.md`. `docs/audio-quality.md` in Vibe has the measurements behind each decoder choice.

| File | Owns |
| --- | --- |
| `AudioFileHandle` | the parser, codec, and descriptor lifetime, the immutable facts, checked seeks, reads, and writes. It owns the one guarded, extension-hinted CoreAudio open (`openParserWithError:`), which a read reaches for a file none of the handle's decoders takes, and which a metadata fallback opens alone (`initParserForReading:`). It reads a file still streaming, and a file on a network mount through its read-ahead (below) |
| `AudioFileHandle+MPEG.m` | dr_mp3's decode: the open, which frames the stream itself, the walk that indexes its frames, a headerless stream's estimated count and its settle, the seek, the reads, and the packet decode |
| `AudioFileHandle+Stream.m` | dr_flac's, dr_wav's, and libvorbis's decode: which of the handle's decoders takes the file, dr_mp3 and libwavpack included, the opens, the close, and the reads. The byte reads they pass the decoders stay in `AudioFileHandle.m` |
| `AudioFileHandle+WavPack.m` | libwavpack's decode: its reader over the stream reads, a hybrid file's correction file, the open and its facts, the reads, the seek, and the restart after an interrupted read |
| `AudioFileHandleInternal.h` | the private header the four share: the ivars the decodes read, the core's reads and waits they call, and the decodes' methods the core calls |

The opener an app passes `files/FileLoading`'s coordinator makes a handle. The handle adopts `ServedFileHandle`, so the loader never names its class.

## The decoders

- **MPEG files (MP1, MP2, MP3) are decoded by dr_mp3**, on both platforms, with no choice. Apple's MPEG decoder offers only 16-bit integer output on arm64, which rounds without dither and clips a master's overs. Its x86_64 build outputs float32 and still clips them. `decoderName` names the decoder.
- **FLAC files are decoded by dr_flac**, with no choice. Its output is Apple's bit for bit at under half the CPU, it seeks without scanning from the start, and it plays legal FLACs Apple's codec refuses. dr_flac answers the file's facts too. CoreAudio's parser opens a FLAC only in a metadata fallback, or once dr_flac has refused it.
- **WAV, W64, RF64, and AIFF files are decoded by dr_wav** the same way, when they hold a coding it decodes. A coding it lacks, such as GSM, stays Apple's. MPEG in a WAV is the exception. It goes to dr_mp3. `dr_wav.c` raises dr_wav's rate limit to 768 kHz.
- **The open picks one of the handle's own decoders by the file's first bytes, before any parser** (`openOwnDecoderInterleaved:`). A RIFF, RF64, Wave64, or FORM header goes to dr_wav. `fLaC`, after any ID3v2 tags, goes to dr_flac. An Ogg file goes to libvorbis. MPEG frames go to dr_mp3, after any ID3v2 tags or in a WAV's data chunk. In a file named as MPEG, the first frame may lie up to 64 KB past the tags, as CoreAudio allows. A file the decoder refuses goes to CoreAudio's parser. The check reads the file's first bytes, and the ten after each ID3v2 tag. The parser reads them anyway.
- **Apple's decoders play only what the handle's own cannot** (`VibeOwnDecoderCoding`, `AudioFileHandle.m`). When CoreAudio's parser opens a file for reading and names a container and coding one of the handle's decoders takes, that decoder has already refused the file. The open for reading refuses it too, with `kAudioFileUnsupportedDataFormatError`. Apple's decoders get the codings the handle has no decoder for, such as AAC, ALAC, Opus, and GSM in a WAV, and the containers it does not parse, such as CAF and MP4. A metadata fallback still reads facts through the parser. A W64's facts come from there, though dr_wav plays it. **TRAP: the parser open parses as the extension's type first**, as `AudioFileOpenURL` does, and by content only after a refusal. Sniffing alone refuses an MP3 with stray bytes between its ID3 tag and its first frame. **TRAP:** CoreAudio's QuickTime reader has no callback open, so a QuickTime file's parser opens by its URL. A transfer's file never takes that road.
- **dr_flac and dr_wav state a file's facts as CoreAudio's parser does**: the format's flags, its packet and frame sizes, its width, and its channel layout. A PCM sample narrower than its bytes keeps its width, high-aligned: 20 bits in 3. dr_wav rounds an AIFF's up to whole bytes, so the open reads the COMM chunk's width itself. An AIFF's layout is its CHAN chunk (`VibeReadAIFFChunk` reads both). A WAV's is its channel mask. A FLAC's follows from its channel count. There are three known differences. The parser calls a sowt AIFF-C's 24 and 32-bit samples 16-bit. The handle states their true width. The parser also ignores an extensible WAV's valid bits and calls 24 bits in 32-bit containers 32-bit. The handle states 24, and a 24-bit device format then carries the file. The source-depth flag names 16, 20, 24, and 32 bits. The parser states no flag for a FLAC of any other depth. dr_flac states the narrowest flag that holds it. An 8 or 12-bit FLAC states 16, and a 28-bit FLAC states 32. With no flag, `audio/Player`'s bit-perfect output would assume 24 and report a 28-bit FLAC as Active. `testOwnDecodersStateWhatCoreAudioStates` compares every field and every surround layout's stereo fold on each fixture. Without the parser, a FLAC opens 3 to 14 times faster and a WAV or AIFF twice as fast (`open.*` in Vibe's VibeBenchComponents).
- **The MPEG open frames the stream itself** (`AudioFileHandle+MPEG.m`). It states CoreAudio's facts and length, except where CoreAudio is wrong. CoreAudio misses the Info frame of a mono or an MPEG-2 file, so it plays their encoder padding. It stops counting packets where a stream changes mode. It refuses free format. The walk takes the priming and remainder from the LAME tag, or from iTunes' iTunSMPB comment. It trusts a Xing, VBRI, or iTunes count only when the count fits the file. The stated bytes must cover the audio, apart from tags after it. Each counted frame must get a size the stream's frames can have. **TRAP: the stated bytes include the Xing, Info, or VBRI frame, and the count does not.** Counted against the frames, they failed every 320 kbps file at 44.1 kHz under 4.5 minutes, and its open walked every frame. The remainder is trimmed only when the stream holds exactly the packets stated. A frame that states no bit rate is free format. It runs to the next header of the stream, never past dr_mp3's largest free format frame, whether the whole stream is free format or damage left one frame so. The channels are the most any frame walked at open holds. A mono frame plays in both channels, and a stereo frame is mixed down. MPEG in another container, such as CAF, is Apple's. `testOwnDecodersStateWhatCoreAudioStates` compares every MPEG fixture.
- **The MPEG open and decode have traps of their own** (`AudioFileHandle+MPEG.m`). **TRAP:** a chain of frames also ends at a tag that ends a file: ID3v1, APE, Lyrics3, or an appended ID3v2 tag. Without the tags, the frames between damage and an ID3v1 tag were dropped. **TRAP:** an ID3v2.2 or 2.3 tag can be unsynchronised as a whole, so it is decoded before the walk looks for iTunes' comment. An ID3v2.4 frame flags its own. Skipping either left an iTunes file playing its encoder padding. **TRAP:** a frame size past what its tag holds ends the tag's walk. In 32 bits, a header plus such a size once wrapped to 0, and the walk never moved. **TRAP:** the comment's words are 64-bit. A priming or remainder past 65,536 frames, or frames past 2^40, is no comment. **TRAP:** dr_mp3 resets itself at a header unlike the one it holds, and finds a free format frame's size only from the next header. So the decode gives it each frame's header, and a free format frame's size, before it decodes the frame. Without the size, every such frame decoded to nothing.
- The vendored dr_ copies carry fixes of Vibe's own. Each one's doc in `third_party/` lists them. AAC decodes to float natively.
- **Ogg Vorbis is decoded by libvorbis on both platforms.** The handle's open gives every Ogg file to vorbisfile (`openVorbisInterleaved:`). vorbisfile finds the Vorbis stream among the streams the file starts, and skips a Skeleton or a video stream. A file with no Vorbis stream, such as Opus, goes to CoreAudio's parser. One vorbisfile refuses is refused. iOS's Ogg reader refuses Vorbis. macOS's decoder starts each file 128 frames late, and `testOggVorbis` fails once it no longer does. vorbisfile answers the facts: the rate, the channels in Vorbis I's order as labels, and the length from the last page's granule position. A chained file plays its leading streams that share the first's rate and channels, since a reader takes one format per file. macOS's parser plays only the first stream of such a chain. The handle counts the position itself, since vorbisfile's follows granule positions, which damage can set to anything.
- **TRAP: a Vorbis open reads the first audio page and the last 64 KB.** A file still downloading needs both. So the tail window `TailWindowMath.h` gives an Ogg file must hold 64 KB.
- **WavPack is decoded by libwavpack on both platforms** (`AudioFileHandle+WavPack.m`). The open gives a file that starts with a `wvpk` block to it, after any ID3v2 tags. CoreAudio has no WavPack parser, so a file libwavpack refuses is refused. It reads through the handle's stream reads, at their cursor, so a file still downloading waits as dr_flac's does. A lossless file states its facts as the WAV it was packed from: PCM of its width, high-aligned in its bytes (20 bits in 3), float or signed integer, and an 8-bit sample unsigned unless its source's was signed. A layout follows from the channel mask, as a WAV's does. The decode scales an integer as dr_wav scales a WAV's, so the two decode one file's samples to the same floats. `AudioFileHandleWavPackTests` checks every width bit for bit. A damaged block's checksum fails, and it decodes as silence. The decode goes on from the next block.
- **A hybrid WavPack file plays lossless when its correction file sits beside it**, and its lossy half alone otherwise. WavPack's hybrid mode splits a song into a small lossy `.wv` and a `.wvc`, the correction. Together they decode bit for bit. "A hybrid WavPack file" below says how the `.wvc` is found, read, checked, and dropped. With it, the file states the source's facts as a lossless `.wv` does, so bit-perfect output keeps its depth. Without it, the file states WavPack's own format ID, `'wvpk'`, and no depth, as a lossy codec does. `correctionFileURL` names the `.wvc` an open decodes with, and is nil for every other open, so an app and its diagnostics can tell the two apart.
- **WavPack DSD plays as 24-bit PCM at an eighth of its DSD rate** (libwavpack's `OPEN_DSD_AS_PCM`): DSD64 at 352.8 kHz, and DSD128 at 705.6 kHz. It states `'wvpk'` and no depth too. DSD256 and up would decode past 768 kHz, the handle's limit, and is refused. `kVibeDecodeMaxRate` (`AudioFileHandleInternal.h`) holds it, and `dr_wav.c` raises dr_wav's to the same. **TRAP: libwavpack's decimator estimates a DSD file's first 9 frames from the frames its first decode holds.** So after a seek into a DSD file's first 16 frames, those frames differ from a read from the start, by 25 µs of warm-up. From frame 16 on, a seek is exact.
- **Multichannel WavPack plays every channel**, up to the handle's own limits, with its mask's layout. A mask that does not count the channels states no layout.
- **A WavPack file whose first block never stated its length**, as an encoder writing to a pipe leaves it, takes its length from its last block. libwavpack reads its last 1 MB at open to find it. Its tail window is still the small one (`TailWindowMath.h`), so a stream of one waits for its download to reach its tail: such files are rare, and a 1 MB window would cost every streamed `.wv`. One whose length cannot be found is refused.
- Ogg Opus is CoreAudio's own reader and decoder, on both platforms.
- **Apple's Opus decoder ignores the header's output gain**, which RFC 7845 says a player must apply. The handle reads it from the `OpusHead` packet at open and scales Apple's decode by it (`VibeOpusOutputGain`). The samples are then bounded at +12 dBFS, as a damaged MP3 frame's are (`kVibeDecodeSampleBound`). `testOpusPlaysAtItsHeaderOutputGain` ends with a canary that fails once Apple applies the gain itself.
- **TRAP: FLAC in Ogg is refused at the parser open**, since that reader reports it no length and decodes only its first page. A metadata fallback opens the same way. `media/Tags`' TagLib wrapper refuses it as FLAC. Its row then fails to parse rather than look playable (`AudioFileHandle.m`, `testFLACInOggIsRefused`).
- **TRAP: a CAF's info chunk is checked before CoreAudio's info parser reads it**, since a forged entry count makes that parser loop forever. `infoDictionaryReadable` walks the chunk headers through the handle's own reads. It answers NO when the info chunk is absent, runs past the file, or declares more entries than its body could hold. A streamed CAF's data chunk of size -1 ends the walk, so an info chunk after it is dropped.
- **TRAP: an MP4's item list is checked before CoreAudio reads its info dictionary too**, since CoreAudio sizes each item's copy from the item's claim. A 1.6 KB M4A with an item claiming 1.38 GB past its end made it allocate and touch 4.3 GB. `infoDictionaryReadable` walks the atoms on the way to `ilst`, each item, and each item's own atoms. It answers NO when any of them runs past its parent or the file. A file cut short outside `moov` keeps its tags. Tests/Fuzz's `tags-m4a` found it.
- **TRAP: a file's ID3v2 tags are walked before CoreAudio's parser opens it**, since its MPEG reader never returns on a tag after the first whose header is cut short by the file's end, or has a version or revision of 0xFF. It sniffs tags whatever the extension. `VibeID3TagsOpenable` reads each tag's header through the handle's own reads, and the open refuses such a file. The metadata fallback opens the same way. Tests/Fuzz's `decode-mp3` found it.

## A hybrid WavPack file

**The correction file is read by a second handle that the WavPack glue owns** (`_wavpackCorrection`, `AudioFileHandle+WavPack.m`). It is an `AudioFileHandle` opened with `initBytesForReading:interrupted:error:`, which opens the file and no decoder. libwavpack reads it through the same reader callbacks as the `.wv`, at the second handle's own cursor. So its reads go through every seam the main file's do, with no new I/O code: the read block, a read-ahead on a network mount, the waits, and the close queue. The core changes in three places only. `interruptReads` and `allowReads` reach the second handle too, and `waitingForBytes` answers YES while either handle waits.

- **Found by name, beside the `.wv`.** The same folder, the same name, and the extension `.wvc`. The spellings are tried in order: the `.wv`'s extension with a `c` in its case (`wv` to `wvc`, `WV` to `WVC`), then `wvc`, then `WVC`. A case-sensitive volume needs all three. A case-insensitive one finds the file at the first. Only a hybrid file looks, after its lossy open, so a lossless or DSD file pays nothing.
- **Checked at open.** The open makes a second libwavpack context over both files, seeks it to the last frame, and decodes it. The correction must hold that block, and the block's checksum, which is the lossless decode's, must pass. A `.wvc` cut short has no last block, and another song's fails the checksum. Then it seeks back to the start. That costs one block's decode, and the reads that find the last block in each file. A `.wvc` that passes replaces the lossy context. A `.wvc` damaged in the middle is not caught. Its damaged blocks play their lossy half, as a damaged `.wv` block plays silence.
- **Any failure falls back to today's lossy play, with no error.** A `.wvc` that is missing, empty, unreadable, cut short, damaged at its end, not WavPack, or another song's leaves the lossy context, opened again, since the check moved its cursor. A fallback decodes exactly as the `.wv` alone. The one exception is an interruption: an open whose `interrupted` block ends a wait on the `.wvc` fails as an interruption, as it would on the `.wv`.
- **A file still downloading plays its lossy half.** A stream (`files/FileLoading`, `files/RemoteFiles`) never looks for a `.wvc`, and a `.wvc` a transfer is still writing is never taken. The lossless decode starts at the next open once both files are on disk. A stream's tail window stays the `.wv`'s alone (`TailWindowMath.h`). Recommended, open to change: a stream would have to fetch and wait for a second file, and a hybrid file is rare.
- **Interrupted reads restart both readers.** A lost or failed read of the `.wvc` is the file's own (`takeCorrectionFault`): the read or seek it happened in answers NO with its error, and the context is stale, so frames libwavpack made without the correction never play as lossless. The seek after `allowReads` opens a fresh context over both files, and both cursors start over. `AudioFileHandleReadAheadTests` interrupts a read waiting on each of the two files.
- **On a network mount, the `.wvc` reads ahead on its own thread**, at the floor's span (`files/FileLoading`, `NetworkReadAheadMath.h`). `holdStream` raises only the `.wv`'s span: a `.wvc` is a fraction of its `.wv`, and its handle states no length to size a span by.
- **Closing.** The context closes first, then the second handle goes. That handle closes its file as any handle does: on the close queue, for an open with an `interrupted` block (Closing a file, below).
- **What an app must grant.** The handle opens the `.wvc` with the process's own rights. A sandboxed app reaches it only with access to the folder that holds it, such as a security-scoped bookmark of the folder or of a folder above it. A single file the user dropped or opened gives access to that file alone, so it plays lossy. An app may declare `.wvc` as a related item type (`NSIsRelatedItemType`) to reach it beside a single file. Recommended, open to change: no piece here does that yet.
- **An indexer's cheap answer.** `+correctionFileForWavPack:` opens and closes each spelling, and reads nothing. It answers whether a play would find a `.wvc`, not whether the `.wvc` passes the check. `media/Metadata` asks it for a hybrid file alone (its AGENTS.md).

## Closing a file

**TRAP: a handle's last release never closes its file on the thread it lands on** (the dealloc). On a network share a close can wait on the server. The pieces let handles go where main waits: under `audio/Player`'s locks at a gapless promote and at a recycle, on its player queue when a parked file is dropped, on the file loader's state queue when an open is abandoned, and under `waveform/WaveformLoading`'s loader lock, which main's cancel takes, when a load ends. So a handle opened with an `interrupted` block hands its descriptor, or its parser opened by URL, to a serial close queue of its own. Its decoders and a callback parser still close in the dealloc, since they read through the handle. No call site needs to carry a release past a lock. A close stuck on a dead server holds the later ones. A handle opened with no block closes its files at its release. An app that moves files after reading them opens that way.

## Reading a file still downloading

**A file a remote transfer is still writing opens as a stream** (`CloudFileMaterializer availabilityForURL:`, `files/FileLoading/AGENTS.md`). The handle reads the part file at the final size. Every callback waits for the bytes it was asked for before its `pread`, never the rest of the block and never a read at or past the size. Or it copies them from the transfer's tail window when the wait says they are there and not on disk. A block fill takes one source, the window's bytes or the disk's. **TRAP:** the transfer can finish and rename its part over the URL between the lookup and the open, so a missing part waits for the transfer's verdict and opens the URL.

A wait ends ready, failed, or interrupted. A failed transfer is a read failure carrying the transfer's error, for good. **Interrupted is neither the end nor a failure.** `interruptReads` (any thread) or an open's `interrupted:` block ends a wait that would block. The read, seek, or open answers NO with an error `isInterruption:` names, and reads are refused until a seek after `allowReads`. **A lost read returns no bytes**, so every decoder sees one clean end of data. That seek restarts the two decoders that keep state across it:

- **TRAP:** dr_flac's seek skips a target it believes it is at and moves inside the frame it holds without reading, so it is restarted at its first frame.
- **TRAP:** ExtAudioFile serves packets the lost read fetched after a later seek, so it is rebuilt over the same parser.
- dr_wav's cursor never moved, and dr_mp3's seek rebuilds its decoder anyway, provided a lost read never shortens the packet count. vorbisfile's seek finds its page again from the bytes. A lost read reaches vorbisfile as a failed read, never as the stream's end (`VibeVorbisRead`).
- **TRAP:** libwavpack keeps the block it was reading when a read was lost, cut short, and a seek inside that block decodes on from it. So the seek swaps in a fresh context, opened as the first was, over a hybrid file's correction file too. A failed seek, and an unpack that stops short of the length, mark the context stale the same way, and reads return nothing until a seek. Without the second, damage that reorders blocks read frames after the end.

**TRAP: an MP3 with no count that fits the file states no packet count.** A count comes from a Xing, Info, or VBRI frame, or from iTunes' comment. The walk counts one by reading every frame header to the end, so a stream of one would open only once downloaded. It opens uncounted instead, on a count from the frames of its head (`estimateMPEGPacketsAtRate:`, `AudioFileHandle+MPEG.m`). The open waits for 16 frames and walks on through those already on disk. If they share the first's bit rate, the count is what that rate gives the audio's bytes. Otherwise it is the count at their average size. **Either is an estimate** (`lengthIsEstimated`), since a headerless file can change rate after its intro. It is kept ahead of the cursor, so a reader never takes it for the end. It is settled from the walk's count when the reads reach the stream's end, or at the first read once the download is complete, on the reading thread. `awaitExactLength:` settles it too, once it has waited for the download to complete. Seeks land exactly either way, since a packet is a fixed number of frames. A head that does not walk is still counted at open, waiting for its download.

- **TRAP:** the settle stores the length, then clears the flag with release ordering, and `lengthIsEstimated` reads it with acquire. A reader of both takes them as one pair (`lengthEstimated:`).
- How the player follows an estimate, and refuses nothing against one, is `audio/Player/AGENTS.md`. `audio/AudioTypes`' CUE window keeps a cue end past an estimate.

A whole file pays one lookup per open and one nil check per fill. The file loader's coordinator opens a readable transfer's file this way and interrupts the open when its run is cancelled. The open's deadline is the app's.

## Reading ahead on a network mount

**A file on a network mount reads ahead** (`files/FileLoading/Transfer/NetworkReadAhead`). The read-ahead itself is `files/FileLoading/AGENTS.md`'s: its thread, its blocks, its retries, and its orphans. The open decides before any I/O, and three things must hold:

- The opener passed an `interrupted` block, and it is not `VibeNeverWaitsForAStream`.
- No transfer's availability answers for the URL.
- The kernel's mount table says the file's mount is a network one (`VibeNetworkReadAheadApplies`).

The file loader's coordinator opens and `waveform/WaveformLoading`'s read ahead. A nil block, as an app's own one-off read may pass, and a metadata fallback read directly. **TRAP: both roads open the file nonblocking.** A FIFO with no writer then returns at once for `fstat` to refuse, and never parks an uncancellable open worker.

**A read the server fails never fails the open.** The read-ahead retries it until its handle is gone. Only the read-ahead's own `open` and `fstat` fail the open, with the direct road's errors. A persistent read error on bytes the open needs is retried, so that open fails at the app's open deadline. A dead server is then a wait, which `audio/Player` turns into a pause.

**Interrupted reads pause the fetch ahead.** `interruptReads` sets the availability's `readAheadPaused`, and the thread then fetches only a range a wait asks for. So a reader that skipped away stops pulling its file over the network. `allowReads` clears it and wakes the thread.

**The handle holds no descriptor.** Every read waits for its bytes in the availability, as a stream's does, and is copied out of the blocks. A wait that is Ready with nothing copied is the end of the file. The open waits for byte 0, then takes the noted size. The open's canceller wakes only a transfer, so the open's waits ask its `interrupted` block again every 0.25 s. Every later interrupt comes with a wake from `interruptReads`. `holdStream` has no transfer to hold. On a play's handle it raises the read-ahead's span to about 30 s of the file instead. That read-ahead then fetches ahead only while the plays' read-aheads sized before it are idle. The playing file's goes before the prefetch's (`files/FileLoading/AGENTS.md`). The QuickTime reader has no callback open, so its URL road finishes the availability first, which ends the thread. **An MP3 is counted exactly at open**, as a local file is. A headerless MP3 whose frames take longer than the open deadline to cross the wire fails to open. `waitingForBytes` rises while a read waits for a block.

**The handle's dealloc finishes the availability first**, with a "closed" error, and only then closes its decoders and parser. The thread exits once its current syscall returns. Until then it is an orphan (`files/FileLoading/AGENTS.md`). An open waits while eight are orphaned, and the app's open deadline still bounds that wait.

## The read-ahead's seam

**`AudioFileHandle+Debug.h` lets a test read a local file as if it were on a share.** `debugSetMountRule:` forces the mount rule per URL. `debugSetBeforeRead:` runs a hook on the read-ahead thread before each `pread`, outside every lock. The hook can throttle a read, stall it until released, fail it with an errno, or end the file there. `debugSetRetryScale:` scales the pause before a failed read is tried again. Two counts are read back: the read-ahead threads alive, and those orphaned inside a read. `debugCloseQueue` is the queue a released handle's file closes on. The rule, the hook, and the counts are process-wide, so a test sets them for its own URLs and clears them in `tearDown`. The category forwards to `files/FileLoading`'s `NetworkReadAhead+Debug.h`, whose statics live in `NetworkReadAhead.m`. The seam compiles in every configuration and wraps its body in `#if DEBUG`.

## Tests

`Tests/audio/Decode/` holds the tests of the handle. `AudioFileHandleTests` covers the open's verdicts, the facts, the reads, the cursor, and the close queue. `AudioFileHandleStreamingTests` reads a file while its bytes arrive, and opens through the file loader's coordinator. `AudioFileHandleReadAheadTests` reads ahead on a forced network mount. Both share `AudioFileHandleStreamingTestCase`, which runs no tests. `AudioFileHandleWavPackTests` reads WavPack, a hybrid file with and without its correction file, and the AIFF-C spellings. Its fixtures are in `Tests/audio/Decode/WavPack/`, since nothing here encodes WavPack. `make-fixtures.sh` there remakes them with the `wavpack` tool, from `make-sources.py`'s integer signals, which the test repeats, so no fixture is anyone's recording. `AudioFileHandleOpenTests` checks that the coordinator delivers a real handle, through the opener `audio/Player` passes. `TailWindowMathTests` checks each format's window. **The streaming tests open a file with a chunk after its audio on the window `TailWindowMath.h` gives it**, so a window too small for such an open fails here. `files/RemoteFiles`' tests check that its store asks for that same window.

They write their own fixtures (`Tests/Support/AudioFileFixtures.h`). `VibeReadAheadScript` (`Tests/Support/`) scripts the read-ahead through the seam. It counts reads by file and offset, and can throttle them, stall them, fail them, or read nothing once. **The read-ahead counts are process-wide**, and a stalled thread outlives its handle as an orphan. A class that parks threads releases them in `tearDown` and waits for `threadsGone` before the next test counts. Vibe's tests compile both helpers from here.

**`AudioFileHandleFuzzTests` feeds seeded mutants of every fixture through the handle.** Each decoder family is a subclass: dr_wav's, dr_flac's, the MPEG decoders', and Apple's. It reads the fixtures an app generates when `VIBE_AUDIO_FIXTURES` names their folder, and the few sources it writes itself. Here nothing generates fixtures, so the dr_flac and MPEG families skip. Vibe's audio suite compiles the same file and runs it over Vibe's generated fixtures. `TEST_RUNNER_VIBE_FUZZ_ITERATIONS`, `TEST_RUNNER_VIBE_FUZZ_SEED`, and `TEST_RUNNER_VIBE_FUZZ_EXPORT` work as the file's header says.

The player's render suite reads files through the handle too. It is `audio/Player`'s, and an app's test target runs it over its generated fixtures. Its `AudioPlayerRenderFidelityTests` holds the decoder tests this doc names, such as `testOwnDecodersStateWhatCoreAudioStates` and `testFLACInOggIsRefused`. Vibe keeps the tests that need its own code: its corpus conformance test, its render suite's link tests, and its Dropbox mirror's streaming tests. The minimal consumer writes a WAV, reads it back through the handle by dr_wav, and checks every sample.

`Tests/Fuzz/` also fuzzes this piece by coverage, under sanitizers, through its `decode-*` targets ([Tests/Fuzz/AGENTS.md](../../Tests/Fuzz/AGENTS.md)).
