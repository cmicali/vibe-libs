# ui/SettingsWindow

A settings window in the System Settings shape, for a mac app. It depends on `ui/Controls` and `core/Graphics`, and on `core/Common` for `NSString+FormLabel`. It holds the generic window, its sidebar, the pane base, the form views, and the walker's debug seam. It came from Vibe. **It is macOS only.** Its files sit in its `Mac/` half. None reads an app's settings, strings, or types. An app pushes in its panes, its strings, and what a change does.

## How an app uses it

- **The window is `SettingsPanesWindowController`.** An app subclasses it, or makes one directly. It passes its panes as groups of tab items, each made by `paneItemWithViewController:identifier:label:symbolName:`. It pushes six strings: Back, Forward, Undo, Redo, the search placeholder, and the no-results line. A subclass adds toolbar items of its own after super's `updateNavigation`.
- **A pane subclasses `SettingsPaneViewController`.** It builds its sections in `loadView`, hands them to `loadPaneWithSections:`, and reloads its controls in `refreshFromSettings`. Each pane is its own class.
- **A pane takes an effects sink at construction**, a block over an integer. The pane base never reads the bits. A write that must change the running app stores its value, then requests its effects through `applyLiveEffects:`. The sink applies them synchronously, on main. A missing request silently breaks the setting.
- **A drag's live work is paced** (`applyLiveEffectsDuringDrag:`). A continuous slider or color well writes its value on every tick. Its effects apply at most every 1/30 s, always with the last value. `didApplyDragEffects:` runs after each coalesced apply, so a pane can redraw a preview. Discrete changes apply at once.

## Window and chrome

- **The split controller must stay the window's `contentViewController`.** The sidebar's tracking separator resolves through it. Hosting its view bare brings back macOS 26's titlebar scroll pocket as a window-wide band. The split items' `titlebarSeparatorStyle = None` governs that band. A `contentViewController` assigned after init does not bind the title, so `SettingsSplitViewController.setTitle:` pushes it.
- **The window title is the title-propagation chain, never set directly.** Each pane's `title` names its sidebar row and the window. `didSelectTabViewItem:` pushes it onto the split controller. The first pane's title is seeded at init, because the initial selection comes before the split controller.
- **The toolbar is icon-only** (`displayMode`). With labels allowed, a unified toolbar reserves a label row whether or not one is drawn. Labels stay set for accessibility.
- **Sidebar rows are built from the tab items**, so order, labels, and symbols cannot drift. Selection syncs both ways through `didSelectTabViewItem:`, which owns only the selection, the sidebar, and the title. The sidebar puts a spacer row before each group's first pane (`groupStartIdentifiers`). It keeps its own row list (`reloadRows`), so a row index is never a tab index.
- **Each tab item has a stable, unlocalized identifier.** A pane is selected by it, and the history records it.
- **Rows are `SettingsAccentRowView`s, whose `isEmphasized` override answers YES**, so the accent stays while the window is unfocused. Setting `emphasized` in `rowViewForRow:` is overwritten on every key-window change. **TRAP: never `reloadData` inside the sidebar's selection callback.** It resets the selection to row zero and reenters. The icon re-tint rides `SettingsSidebarCellView.setBackgroundStyle:` instead.
- **Search** is the sidebar's field. Typing narrows the rows to the panes whose `matchesSearch:` answers: the pane's title, or a row's title, caption, or section header, ignoring case and diacritics. Every pane marks its matching rows (`setSearchHighlight:`). A pane walks its view tree for rows once, since rows never change after `loadView`, only their visibility. It answers each query once for the filter, the marks, and the reveal. A pane off screen keeps the query and marks its rows when it appears. A pane on screen reveals its first hit, scrolling only when that hit changes. **TRAP: the reload and reselection post selection changes**, which are ignored under `_reloadingRows`. Treated as the user's, one would switch panes under the search being typed. A pane whose sections hide for a reason other than a page swap excludes their rows (`isRowSearchable:`).
- **Back and Forward are System Settings' history** (`updateNavigation`). Every pane switch or page swap pushes the location it left and clears Forward. A location is a pane identifier, or the identifier and the page the pane reports through `currentPage`. The pill walks the history under `_restoringLocation`. That flag also keeps the switch's own refreshes from recording a half-applied state. `goToLocation:` sets the page through `showPage:` before selecting the pane. **A pane picked in the sidebar opens at its top** (`paneWillBecomeSelected:` shows page nil). Only Back and Forward reopen a page where it was left.
- **Undo routes to the selected pane.** A pane that keeps its own `paneUndoManager` gets Edit > Undo while it is selected. A text field's own undo comes first.
- Pane switches are immediate (`transitionOptions` is `None`). The default crossfade composites two section headers and reads as a flash.
- **An app names the window's frame autosave key**, through `NSWindowController`'s own `windowFrameAutosaveName`, right after init and before the window first shows. The window sets none itself, so a window with no name saves no frame.

## The form views

A pane is a stack of `SettingsSectionView`s of `SettingsRowView`s (`SettingsFormViews.h`): cards of hairline-separated rows, with the title and an optional caption leading and the controls trailing. Every flat surface is a `SettingsFillView`, a layer fill re-resolved on an appearance flip.

- **Row titles and section headers drop a trailing colon at display time** (`NSString+FormLabel`, in `core/Common`). One rule covers French's no-break space and CJK's fullwidth colon. An app's iOS screens can share the rule, since `core/Common` builds on both platforms.
- **A `SettingsColorRow` is a row of captioned color wells bound to the pane's model by a read block, a write block, and a change block.** It owns the wells' refresh, their seed, and the hex copy and paste, and knows nothing of what it edits.
- `switchWithAction:` makes a `VibeSwitch`, never an `NSSwitch` (`ui/Controls/AGENTS.md`). `popUpButtonWithWidth:action:` makes a `VibeInlinePopUpButton`, the System Settings inline style, where the width is a cap rather than a size. `detentSliderClusterWithDetent:` makes a `VibeDetentSlider` beside a readout.
- Every list uses `SettingsRowView.listTableWithColumnIdentifiers:delegate:` and `listCellWithIdentifier:inTableView:imagePosition:`. A list inside a card is `SettingsRowView.rowWithTableView:rowCount:`. Its scroller is legacy style, so a list with more rows than fit shows the bar without a scroll, and still hides it while every row fits. `listRowViewForRow:` supplies the shared palette: alternating backgrounds and a neutral selection fill, with no row separators. The palette is measured in Display P3 from the system's Sound settings.
- Disabled controls go through `SettingsRowView.setControl:enabled:` (one control) or `setControlsInView:enabled:` (a row or a section). A disabled control fades to 50% alpha. A row whose controls are all disabled dims its title, caption, and readouts the same way. Separators do not dim.

**TRAP: a content row must never carry a required width, fixed or capped.** `rowWithContentView:` pins its content leading to trailing. The pin climbs to the window's content view, which follows the frame only at `NSLayoutPriorityWindowSizeStayPut`. The content then stops short of a widened window, on every pane. A wrapping explainer (`wrappingLabelWithString:`) follows its frame in `viewDidLayout` instead, with compression resistance below the fitting priority.

## Pane sizing

**Every pane shares one size, the largest pane's, and it is the window's FLOOR, not its size.** `naturalPaneSize` takes its **width from the pane view and its height from the section stack**. It is floored at `kSettingsPaneWidth` × `kSettingsPaneMinHeight` and capped at `kSettingsPaneMaxHeight`. `applySharedSizeToPanes:` writes the maximum into each pane's `sharedPaneSize`. The tab controller turns the selected pane's into `contentMinSize`, which only grows the window. The floor is recomputed, not a high-water mark, so a row reveal raises it and hiding the row lowers it. The window keeps any larger size the user gave it.

- **TRAP: the width has to be the pane's.** A page swapped in beside the stack keeps its required width while hidden. A floor from the stack alone would let the window sit narrower than the pane, clipping every trailing control on every pane. The height stays the stack's, because a swapped-in page scrolls.
- **TRAP: `loadView` runs before `resolveLayoutStateFromSettings`, so a row that hides itself is first measured visible.** `settleSharedSizeForPanes:` runs at window creation. It loads every pane and resolves its layout state before taking the maximum, and it starts no refresh work in a hidden pane. `paneContentDidChange` re-derives the shared size after each refresh or row toggle of the selected pane.
- Each pane scrolls a flipped `SettingsStackView` in a scroll view pinned below the safe-area top. **Every scroll view in this window sets `autohidesScrollers`.** AppKit's default draws a bar down a pane, the sidebar, or a list with nothing to scroll.

**Each pane measurement takes two Auto Layout solves.** Remeasurement has three gates.

1. A hidden window does nothing. `showWindow:` settles every pane on the way from hidden to shown.
2. **A pane remeasures only when its layout signature moved** (`layoutSignature`: which rows show, and the text of their titles, captions, and controls, lists excepted). Every regained key and closed menu refreshes the pane, so this gate is what keeps those cheap. The first open measures every pane, and a reopen measures none that did not change.
3. A pane whose signature moved measures **itself first**. It stops there when its own natural size did not move, since the shared size is a maximum.

**TRAP: a status line that changes often must never reach the solve.** Without the gates, every such change re-solves every pane inside a resize animation on main. Before any of it, `setCaption:` answers whether the row's *height* changed, measured on that one label at its wrapping width. A caption with unchanged height needs no pane measurement. The cost of the gates: a pane whose rows changed while it was not selected can leave the floor stale until it is selected again or the window reopens.

The selected pane calls `refreshFromSettings` on appearance, on regaining key, and after menu tracking ends. The queued menu refresh re-checks visibility, since the menu action may have closed the window. `refreshSelectedPane` is the same entry for an app's own triggers. The sizing pass never calls `refreshFromSettings`.

**Hidden panes start no periodic refresh work.** The controller and every pane outlive the window, so everything that reaches a pane from outside must be gated on the pane being visible. A hidden pane catches up in `viewWillAppear`. Every refresh does nothing on unchanged values: `setCaption:`, `setRowTitle:`, `setControl:enabled:`, and the popup selects return before touching a view. A visible pane's own size change remeasures only itself and reuses its siblings' last measurements (`applySharedSizeToPanes:measure:`).

## TRAP: the fitting-size snap, and the one resize path

AppKit resizes a `contentViewController` window to its fitting size after every layout pass. No constraint arrangement survives that and stays resizable. Equalities collapse the user's resize range, and minimums lose the fight. On macOS 26.5 a child's nonzero `preferredContentSize` becomes priority-501 equalities that pin the window. So the panes carry no size constraints, and the snap is refused at its funnel. **`SettingsWindow` overrides `setFrame:display:`** and drops any size change that is not the user's live resize, a call inside `resizeUnlocked:`, or setup before the window is visible. `resizeUnlocked:` is block-scoped and synchronous. A time-boxed unlock would let the snap back in, and an animator's later frames would arrive locked out. Every programmatic resize goes through `applyWindowFrame:` or `applyContentSize:`. The floor lives only in `contentMinSize`. Zoom is refused.

- **The pane's root view follows the tab view by autoresizing mask, never by host constraints.** The tab controller pins only the pane selected before the window existed. Later selections set a frame and add nothing, so a pane without the mask collapses when selected second.
- **A real shared-size change is `paneContentDidChange`'s alone.** It runs one `NSAnimationContext` at `kWindowResizeAnimationDuration` (`ui/Controls`' `WindowAnimation.h`) with implicit animation. The remeasurement, the pane layout, and a synchronous `setFrame:` through `applyContentSize:` all run inside it. The target frame comes from the engine's own numbers, since anything else is re-snapped by the next flush. **TRAP: the section stack must stay layer-backed.** Implicit animation moves only layer-backed views, and plain section headers would jump.
- **Both the tab and split controllers swallow `setPreferredContentSize:`**, since AppKit resizes the window at once on it. A pane's size change reaches the window only through `SettingsPaneSizeHost`. The tab controller answers it by resetting `contentMinSize` and growing the window where needed.

## The walker's debug seam

`SettingsFormViews+Debug.h` is the generic half of an app's settings walker. `+[SettingsRowView debugElementsInView:]` lists every control under a view as a `VibeSettingsElement`: its view, its kind, its name, its row's label, and its row. A row's title labels the controls beside it. A section's header labels the untitled rows under it. A button names itself. A control's own subviews and a scroll view's scrollers are not elements. **A pane built from anything but these form views loses its by-name addressing.** An app's debug channel matches names, writes replies, and drives the controls.

**How a seam builds here.** Its header has no `#if DEBUG`, since no header here may carry one. Its `.m` wraps its whole body in `#if DEBUG`, so a release build compiles an empty object and ships none of it. This repo's tests build Debug, so they test it. An app's debug configuration must define `DEBUG`, which XcodeGen's debug preset does. A call from code that also builds in release fails to link for the element class. A call to the category method fails only at run time. So only debug-only code calls a seam. The template compiles the seam in every configuration, because a template cannot know an app's configuration names.

## Tests

`Tests/ui/SettingsWindow/Mac/` holds the form views', the window's, and the seam's tests. They run on macOS. The form views build with no window. The fill renders into a bitmap through the shared `Tests/Support/DrawnViewTestSupport.h`. The window tests build the generic window over two panes and never show it. They drive the sidebar's table, the history, and the search in code. Creating the window needs a window server session, which a logged-in Mac and CI's macOS runners have. NSApp is nil, so a sent action is called by hand.
