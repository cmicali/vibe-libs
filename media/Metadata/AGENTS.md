# media/Metadata

The tag record and its CoreAudio fallback, the disk cache of tags, the background scan, embedded art and the shared row thumbnails, and covers beside the files. It holds the metadata pipeline, a client's reads by URL, and the cache's and the loader's debug seams. It came from Vibe. It depends on `core/Common`, `audio/AudioTypes` for the playable item and the format names, `audio/Decode` for the fallback's handle, `media/Tags` for the TagLib parse, `files/DiskCache` for the store, `files/FileLoading` for the materialization and the ranged read, `core/Graphics` for the image helpers, and `third_party/taglib`, whose own headers the parse reads. The import reads its old stores' folder and file names from `files/DiskCache`'s `VibeLegacyCacheNames.h`, since PINCache itself is gone. It reads no app's settings, strings, or types. It builds on both platforms, and no file needs a platform half. **TRAP: an app that also takes `VibeLibsVorbis` or `VibeLibsDecode` lists this template after them**, as it would `VibeLibsTags` (the template's comment).

**What an app gives it.** Its items, any object adopting `AudioTrackMetadataHolder` (below), or for files it tracks itself, their URLs alone (Reads by URL, below). A cache root, or nil for the user's Caches directory. Folder art's two answers, its switch and its access check, as blocks (Folder art, below). The tracks near the one playing, as they change. How Vibe's shells drive it, and the guarantees Vibe states over it, are Vibe's `Audio/AGENTS.md`.

**Artwork is the one place it hands out UI types.** It returns `NSImage` on macOS and `UIImage` on iOS, through `core/Graphics`' `VibeImage`.

## Files

- `AudioTrackMetadataCache` is the facade, and `AudioTrackMetadataLoader` the one sweep behind it (private). Its disk cache sits under the root `initWithRootPath:` names. Nil, which `init` passes, is the user's Caches directory. The disk cache is one store (The store, below).
- The loader is one object in four files. `AudioTrackMetadataLoader.m` is its life and the sweep's stage 1. `+Materialization.m` is the lane: priority marks, the two slots, the foreground gate and each completion's settlement. `+Parse.m` is the cache read, the parse, installation, settlement and publication, with the art's providers. `+Reading.m` is a client's reads by URL. `AudioTrackMetadataLoader.h` is the API the cache and the tests use. `AudioTrackMetadataLoaderInternal.h` holds its ivars and the methods its files share. `MetadataScanEntry` holds its two records, the scan entry and the priority mark. Its debug seam is `AudioTrackMetadataLoader+Debug`, beside it, and the cache's is `AudioTrackMetadataCache+Debug`. Each header declares its surface in every build, and each implementation wraps its body in `#if DEBUG`.
- `AudioTrackMetadataHolder` is what the loader takes of an item. It extends `VibePlayableItem` with the installed metadata, the install that happens only while the item has no answer from the same version, and the delivery that runs only while that answer is still installed. The holder keeps the check and the store under its own monitor, which must be recursive. It is this piece's own protocol (the plan's seam 22), so the playable item stays free of metadata.
- `VibeMetadataRead.h` is a read's policy, its outcome, and its answer for one file, `VibeMetadataReadResult`.
- `MetadataParseCoordinator` is the per-path owner/waiter table and nothing else.
- `VibeMetadataStore` is the disk cache's storage: one `files/DiskCache` `VibeCacheStore`, in bytes. The loader archives and decodes the tags. `VibeMetadataImport` brings the PINCache stores of the releases before it over, then removes them (The store, below).
- `AudioTrackMetadata` is the immutable tags plus the display-facing art API. `AudioTrackMetadataInternal.h` is the loader's construction surface: the parse, the artwork, and the version stamp.
- The TagLib side of the parse is `media/Tags`: `TagLibAudioFile`, the file factory, the ranged stream, the format name and the embedded art's bytes. It reads from disk, or through a byte-range reader the caller passes. `AudioTrackMetadata.mm` chooses the reader and turns the art read into the artwork's extractor (`VibeTagLibArtExtractor`). The parse reads the tags from TagLib's own types, which the map allows. The title and the artist come from the tag, and every other field from one property map (The tag fields, below). The wrapper answers what no tag holds: the format, the art, and FLAC's audio MD5. The wrapper's header is C++, so only `.mm` files import it. `media/Tags`' `NSString+CPPStrings` turns TagLib's UTF-8 into a string, embedded NULs kept.
- `AudioTrackArtwork` is one row's art lifecycle (private behind the metadata). `ArtworkLoadRegistry` is its admission counters, a file boundary, not a second owner.
- `AudioTrackArtwork` is one object in two files. `AudioTrackArtwork.m` is the art state, adoption, the archived display art, demotion and the row thumbnails. `+Loading.m` is the full-art load: the extraction gate, the blocking read ladder and the async load the registry admits. `AudioTrackArtworkInternal.h` holds the ivars and the methods both files share.
- `EmbeddedThumbnailCache` is the decoded thumbnails every row shares, in one bounded LRU.
- `ArchivedArtShare` is a picture's archived forms, shared by the files that embed it (Embedded artwork, below).
- `NSURL+FilenameTitle` is the title a file's name gives, which a parse without a tagged title keeps.
- `VibeTrackDisplay.h` is what a row shows of a track, a whole file or a CUE window of one: its title, its artist, and its length. A sheet's title and performer win over the file's tags, which name the whole image, and a window with an end is its own length. A title only the file name gives is nil, so each app shows the name its own way. It came from Vibe's row.
- `AlbumGroupingRules.h` is which album a track belongs to (The tag fields, below).
- `Artwork/FolderArt/` is the cover fallback (Folder art, below).

**Do not add a runner, driver or second coordinator.** Straight-line metadata work goes in the loader, per-row art work in `AudioTrackArtwork`.

The comments and this doc cite seven lettered items of Vibe's `docs/file-loading-spec.md`. A1 is cited only here. In short:

- **A1.** A local file never starts a transfer. Every rule that bounds or suspends downloads exempts it.
- **C3.** A metadata request for the file playback is downloading joins that materialization. A remote tag parse reads by range instead.
- **D3.** The current track's tags and art come ahead of the sweep, at user-initiated priority.
- **D7.** Retries are per path and driven by results. A yield spends nothing. A failure spends one attempt of the path's budget. Success clears what the path spent. A path that spends its whole budget is dropped until a fresh playlist load.
- **D10.** Opening or replacing a playlist drops the old sweep outright: its pending records, its transfer, and its strong references to the old tracks.
- **J4.** The sweep submits no dataless record while the foreground rule holds, even the file playback is downloading. The current track's request submits and joins that claim instead.
- **J6.** An art request past the bound is dropped before it marks its row pending. The next redraw asks again.

## The scan

**A metadata request may start before a file is materialized. A TagLib parse may not.** The disk-cache check never reads audio, so known rows populate without touching their files. On a miss, `AudioFileMaterializationCoordinator` must report `Ready` before the parse enters a worker.

**The one exception is a remote placeholder of a format TagLib parses.** The rule is `PlaceholderFiles readsRemotePlaceholderByRange:`, over `PlayableExtensions.tagParsed`, and the art loader shares it. Other formats take CoreAudio's facts, which need the whole file, so they materialize. The scan settles such a placeholder Ready with no claim (`submitMaterializationForEntry:`). `AudioTrackMetadata.mm` passes the backend's read (`remoteReadForURL:`) to `TagLibAudioFile`. The wrapper reads through it in blocks, following the parser's reads, artwork included (`media/Tags/AGENTS.md`). A file the backend is streaming is read from the stream, at no request cost. A server that ignores the range sends from the start. The client skips to the requested offset and cancels once it has the requested bytes. A tail read can therefore transfer most of the song. It takes no claim because stage 1 is one claim per path shared by every role. A metadata Ready on a placeholder would hand a playback open joining that claim an unreadable file. It is still a network read, so the foreground rule below gates it.

**The playlist sweep has two stages, and only stage 2 can download.** Stage 1 checks every file against the cache once, behind an operation-queue barrier that waits for enumeration and every check. Stage 2 admits the misses. **A record is a file, not a row.** The rows sharing a standardized path (a cue sheet's forty, a file listed twice) are one record: checked, materialized and parsed once, with its answer copied to every row. A failed parse gives its fallback to the row it read for (the marked row when there is one) and requeues the rest as a record of their own. The scan registers exactly one `MetadataScan` materialization at a time.

**The current track is not a second lane. It is the record holding a row the loader has marked.** It materializes through its own slot beside the scan's, skips the stage-1 barrier, and is submitted even under the foreground rule, since a same-path playback claim serves it for free (spec J4). It parses at user-initiated QoS. Demotion removes the mark, and so does removing the marked row (`abandonQueuedTrack:`), since a marked URL holds its file's other records out of the scan. Every mark carries a generation and its exact target track, and settlement retires only a mark it resolved. A repeat edge reactivates one submission so it can join a new same-path foreground claim. Both slots spend the one per-path retry ledger. A `loadMetadataNow:` before any sweep builds a loader over that one track. The real sweep replaces it and re-prioritizes the weakly held current track. `cancelScan` drops every pending record, priority included, so replacing the playlist drops the old playlist's downloads. It detaches central tokens without cancelling a same-path foreground owner.

**`loadCachedMetadata:` is the cache check alone**, for rows whose audio is not on the device, such as a file browser's placeholders and dataless files. A hit installs and publishes as the sweep's does. A miss ends there, with no record, materialization or parse (`loadFromCacheOnly:`). It runs on a loader of its own that is never cancelled, so a later `loadMetadata:` or `cancelScan` cannot drop a lookup the caller will not repeat.

**The foreground rule is the coordinator's. This piece only asks** (`files/FileLoading/AGENTS.md`). The sweep asks `isForegroundTransferActive` before submitting a dataless record, and re-asks on a bounded 1 s clock while gated (`recheckForegroundGate`, the seam the tests drive). Cache checks continue while gated. **An already-local file is exempt**, so on a partly downloaded folder local tags land straight through. The loader probes locality with `PlaceholderFiles.isDatalessFile:` at every enqueue, submit and requeue, because the playback open routinely downloads the very file a yielded record waits on.

**Materialization results, not error text, decide retries** (`MetadataRetryRules.h`, tested):

- `Yielded` spends no attempt, and a scan record requeues at its rank. A yielded **priority** record is re-judged on each gated tick. Local now, it retries at once (spec A1), since waiting cost the now-playing tags the successor's whole prefetch. Still dataless, it waits rather than re-pick, since a re-pick installs a fresh `Probing` claim and yields again. At the **first idle tick**, still dataless means the open failed, so it demotes to an ordinary sweep candidate.
- `Failed` spends the bounded per-path budget and re-enters below untried rows. `AdmissionExhausted` spends the same budget after a 0.25–2 s delay.

A loader snapshots `AudioLoadingConfiguration`, so a settings change reaches only later loaders.

**Pending misses are records picked one at a time, never sorted** (`MetadataScanOrderRules.h`, tested): already-local first, then untried before deferred, then neighborhood rank, then playlist index. A real playlist holds more than 100,000 misses, so a track change replaces only a small locked neighborhood snapshot and enqueues a coalesced kick. An app sends the snapshot through `setNeighborhoodTracks:` when its current track changes. It hands over the next few tracks in play order, so shuffle ranks what will play, never the whole list.

**The cache key is the item's `cacheKey` (`VibePlayableItem`).** An item may memoize it until a download installs another version than its placeholder's (`files/FileLoading/AGENTS.md`). Then every memo is retired and the next lookup stats the file again. Each installed metadata carries the key it was read under (`AudioTrackMetadata.cacheKey`). A row whose key no longer matches it is parsed again in the next sweep, and the new version's answer replaces the old one. A priority edge does not check the version, because it runs on main and must not stat.

**A load never runs ahead of the store.** The cache opens its store on its own utility queue after init, since the open does a few milliseconds of disk work. Every block on that queue gets the store through `storeOnQueue`, and the first to ask builds it. A read of the store before it exists makes that call through `dispatch_sync` on the queue (`metadataCache`). The store then exists when the read returns, whichever block the queue runs first. The `dispatch_sync` also lends the reader's QoS to the queue, and so to the build. A `dispatch_group` wait would lend none. A `dispatch_block_wait` crashes on a block's second wait, and several workers can wait at once. So a load issued at once after init is looked up and filed like any other. There is no "ready" signal, because no caller can race the store. A waiter would grow the API, and every caller would have to remember it. Only a read that races the build waits, and only once. The waiting reads are the loader's workers. Main never reads the store, so `loadCachedMetadata:` enqueues its lookups straight from main.

**TRAP: a parse's version is checked at its completion, never at its start.** The key is taken before the read. A placeholder's parse can read from the download that installs another version, and that download re-keys only when it ends. At completion the loader reads the item's `cacheKey` again and compares it with the key the parse was looked up under. On a mismatch the result is neither installed, delivered nor filed, since its bytes may be either version's. The record, with the claim's waiters, parses once more under the new key (`AudioTrackMetadataLoader+Parse.m`). It is not requeued through the lane, because the new version is already on disk and the lane would drop a priority record's mark. The item's key is compared, never a fresh stat, so the next parse is keyed as the check is.

## Reads by URL

**`readMetadataOfURLs:policy:deliveryQueue:result:completion:` reads tags for files a client tracks itself**, such as a library's index, which keeps no holder per file. It is the loader's straight-line path, with no record, mark, materialization, or delivery to main (`AudioTrackMetadataLoader+Reading.m`). The cache builds one reading loader on the first read, and never cancels it, so `loadMetadata:` and `cancelScan` cannot drop a read. Any thread may call it.

- **Each URL is answered once**, as a `VibeMetadataReadResult`, on the caller's serial queue. The completion runs there after the last answer. The outcome says why a file has no tags: missing, a cache miss, unreadable, not parsed, changed during the parse, or cancelled. Nothing is held once the completion has run.
- **The disk cache comes first, under the file's `cacheKey`.** A miss parses the file, and a successful parse is filed, so a sweep finds it too. A failed parse is never filed, as in the sweep. A row of an older format is a miss for a read that may parse, and the answer for one that may not, marked `older` (The store, below).
- **The policy says what a read may open.** `Local` parses only a file on this device. A placeholder, a provider's or a remote one, gets the cache alone. `CacheOnly` never opens a file.
- **A parse runs with materialization off for its thread** (`IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES`). A file the provider frees after the check then fails to read, rather than downloads, and its answer is a cache miss. Measured on macOS 27.2: under the policy, opening an iCloud Drive or a Dropbox placeholder succeeds, every read fails with `EDEADLK`, and the file stays a placeholder. **TRAP: the policy is the thread's, and is restored after the parse**, since the queue's thread runs other work next.
- **Only a regular file reaches the parse.** The reader opens the file with `O_NONBLOCK` and checks it with `fstat` first. A file it can't open is Unreadable with the open's error. A FIFO, a directory, or a device is Unreadable with `EFTYPE`. **TRAP: the parse reopens the path with a blocking `fopen`**, so a FIFO under an audio name would hold its worker until a writer came, and no cancel reaches a begun parse.
- **Each file's temporaries are drained before the next.** **TRAP: a worker reads each file inside its own autorelease pool.** The parse autoreleases its display-art rendition through an out-parameter, so without the pool a worker would keep every file's buffers until its whole list was done.
- **No transfer, so no foreground rule.** A read never materializes, so it never competes with a playback open (spec A1).
- **It joins no sweep's parse.** The parse coordinator's waiters are holders, delivered through a loader. A read of a file a sweep is parsing at that moment parses it once more, and both file the same entry. A URL given twice is read twice.
- **The version is checked at the parse's completion**, as the sweep's is. A file whose key moved during the parse is answered Changed, and nothing is filed.
- **The parses run at the configured local parse concurrency**, at utility QoS, on the reading loader's own queue. A call takes no more workers than that, however many URLs it gives, and its workers walk its list. Cancelling the call's progress answers each file not begun as Cancelled. A parse already begun finishes.

## Duplicate rows and delivery

**One parse per standardized path** (`VibeStandardizedAudioOpenPath`, the spelling every loader identity uses). `MetadataParseCoordinator` holds duplicate rows weakly as waiters. The owner rechecks the disk cache after claiming, since another lane may have won. Its answer is copied into every unresolved waiter while the holder still gates new owners, and the last empty drain releases the claim before publication. Each copy has its own artwork state.

**A DSD file's facts are its DSD's, not the PCM it plays as.** Its `sampleRate` is the DSD rate, such as 2,822,400 for DSD64, where `audio/Decode`'s handle states 176.4 kHz (`media/Tags`' `VibeSampleRateFromTagLibFile`). It is lossless, and its bit depth is 1. A DSF's kind is DSD, and its bit rate is the DSD rate times the channels. A WavPack DSD file's kind is WavPack, and its bit rate is TagLib's, the file's, since WavPack compresses DSD as FLAC does PCM. **TRAP: TagLib's bit rate multiplies by the fmt chunk's bits per sample, which is the bit order**, so a file stored most significant bit first read 8 times too fast, and the parse computes it instead. An app names the rate with `audio/AudioTypes`' `VibeDSD.h`.

**A file TagLib has no parser for takes its facts from CoreAudio's**: CAF and W64 among the playable ones, and any file TagLib refuses that CoreAudio reads. CoreAudio has no WavPack reader, so a `.wv` TagLib refuses fails its parse, though `audio/Decode`'s libwavpack may still play it. Those are duration, rate, bitrate, the codec or container name, and the info dictionary's title and artist, with no art. It parses OK, caches, and the folder's cover can stand in (`loadCoreAudioFactsFromURL:`). It reads them through `AudioFileHandle`'s `initParserForReading:`, CoreAudio's parser with no decoder. **TRAP: the handle closes its parser when it is released, so its lifetime is pinned to the read's scope.** ARC may release it right after its last message. The verdict is CoreAudio's. Playback opens FLAC, WAV, W64, RF64, AIFF, Ogg Vorbis and MPEG with `audio/Decode`'s own decoders. It can disagree with CoreAudio on those.

**TRAP: a CAF's info chunk and an MP4's item list are checked before CoreAudio reads them.** CoreAudio's CAF info parser loops without end on a forged entry count, and the hang holds a metadata worker forever. Its MP4 reader sizes an item's copy from the item's claim, so a small file can make it allocate gigabytes. `loadCoreAudioFactsFromURL:` reads the info dictionary only when the handle's `infoDictionaryReadable` says so (`audio/Decode/AGENTS.md`). The format facts still come from CoreAudio.

**The fallback opens never wait for a download or read ahead.** Both pass `VibeNeverWaitsForAStream`: CoreAudio's facts open and dr_flac's FLAC-length open (`AudioFileHandle.h`, compared by identity). Against a file a transfer is still writing, the open fails at once, and the facts come once the file is on disk. On a network share the open reads the file directly, as TagLib's parse does.

**TRAP: the TagLib parse must refuse what that open refuses.** TagLib's FLAC sniff takes FLAC in Ogg, which playback refuses. So the wrapper parses no Ogg stream as FLAC (`media/Tags/TagLibAudioFile.mm`). Such a file is a failed parse, not a row that looks playable.

**A file neither parser reads produces uncached fallback metadata.** An exception after partial parsing can leave some facts installed. Neither fallback nor partial results enter the cache. The holder and every waiter get their own fallback copies, so no row stays unresolved. Installation and publication compare the exact metadata object under the track monitor. A racing success replaces a fallback, and the stale fallback's delivery drops.

**Every delivery runs on main and revalidates the exact installed object while holding the track monitor through the delegate call.** Delegates may update UI synchronously. They must never wait on a metadata worker.

## The tag fields

**The record holds the fields a library app reads.** Beside the title, the artist, the tempo, and the key, it holds the album, the album artist, the genre, the composer, the year, the track and disc numbers and counts, and the compilation flag. It holds the comment, the grouping, and the record label. It holds MusicBrainz's release and recording identifiers and the ISRC. It holds the rarer tags an editor shows: the catalog number, the conductor, the remixer, the lyricist, the mood, the language, the copyright, the original date, and the sort names of the title, the artist, the album, and the album artist. It holds FLAC's audio MD5, and the bit depth. It holds the loudness tags: ReplayGain's track and album gain and peak, Opus's R128 track and album gain, and Apple's Sound Check. A field the file lacks is nil, 0, or NO.

Opus defines the R128 gains. The parse reads them from any Xiph comment, since the lookup is the same. A count comes from the number's tag, as in "3/12", or else from a tag of its own. The year is the date's leading number. **ID3v2's `TIT1` is the grouping only when `GRP1` is absent.** TagLib calls `TIT1` the work, as iTunes has since 12.5. Before that, iTunes kept the grouping there, and many taggers still do. MP4's and a Xiph comment's work is never the grouping. An ID3v2 comment with a description, such as iTunNORM, is not the comment.

**The rarer tags share one dictionary, `extraTags`, keyed by TagLib's property names.** Each is rare, so a dozen properties would cost every record a dozen pointers for nothing. The dictionary holds only the tags the file carries, and is nil when it carries none, so an untagged record pays one pointer. The archive files it only when present. An app reads one with `extraTag:`, by a `VibeTagField` constant from `media/Tags`' `VibeTagFields.h`, the names the writer takes, and `VibeMetadataExtraTagNames()` lists the ones filed here, so no caller spells a name. The parse reads every field by those constants. `originalYear` is the original date's leading year. A tag of blanks is untagged, never empty. The keys are the names TagLib's writers take, so an app writes a field back under the name it read it by. ID3v2.3 has no `TMOO`, and TagLib's v2.3 writer drops it, so a v2.3 mood lives in `TXXX:MOOD`, which the same lookup reads. TagLib's v2.3 writer keeps only the original date's year, as `TORY`.

**`ratings` holds every rating the file holds, as stored**, by `media/Tags`' `VibeTagRatingFields`, from the property map the parse builds once: each POPM frame's byte under `POPM:` and its email, MP4's `rate` atom as `RATING`, `RATING` and `FMPS_RATING` from the format's own tag, and a Xiph comment's or a WavPack or Monkey's Audio file's APE tag's `RATING:<email>`. At most 32. It is nil when the file holds none, and the archive files it only when present. It interprets no scale: which rating an app trusts, and what it means, is the app's (`media/Tags/AGENTS.md`, Ratings).

**Each gain keeps its own reference level.** A ReplayGain gain is the tagged decibels, toward ReplayGain's reference. An R128 gain is Opus's Q7.8 whole number over 256, toward −23 LUFS, on top of the header's output gain. Sound Check's gain is −10 log10 of the louder of iTunNORM's first two words over 1000. Peaks are linear, with 1 at full scale. An app that levels by them converts between references itself.

**FLAC's audio MD5 comes from STREAMINFO**, through the wrapper's `audioMD5FromTagLibFile`. It is the MD5 of the decoded samples, so a retag never changes it. An encoder that computed none writes zeros, which read as nil.

**The bit depth comes from the stream, through the wrapper's `bitsPerSampleFromTagLibFile`**: FLAC, ALAC or FLAC in MP4, PCM or float WAV, AIFF, and lossless PCM WavPack. DSD reads 1, in a DSF or a WavPack file, and so lossless, but for a DSD WavPack file that says hybrid, which `audio/Decode` refuses. **A hybrid WavPack file reads its source's depth, and so lossless, only while its correction file opens beside it**, since `audio/Decode` then plays it lossless. The parse asks `AudioFileHandle`'s `correctionFileForWavPack:`, the play's own search, which stats each spelling of the `.wvc` and reads nothing: a regular file of some bytes, on this device, that no transfer is writing. It asks only for a hybrid file (`VibeWavPackHybridBitsFromTagLibFile`), so no other file pays for it. A file still downloading reads lossy, as it plays. The check does not decode, so a `.wvc` that is there but cut short or another song's reads lossless while a play falls back to lossy. **The disk cache keys a hybrid file by the `.wv` alone**, so its answer is the one from its last parse. An app that watches its folders parses the `.wv` again when its `.wvc` appears, changes, or goes. Recommended, open to change: a key that also named the `.wvc` would cost every file a second stat. CoreAudio's facts give it for PCM, and for ALAC by its flags. A lossy codec has none, so it reads 0, though an AAC sample entry names 16 bits.

**WavPack DSD's answers came with no bump of `VibeMetadataTagsFormat`** (recommended, open to change), since no app had shipped WavPack playback, and a bump parses every file of every library again. A row parsed before them keeps 0 bits and the byte rate until its file is parsed again.

**CoreAudio's facts carry none of the fields.** A CAF or a W64 reads its title and artist from the info dictionary, and no other tag.

**TRAP: an entry archived before the fields must not read as untagged.** It decodes cleanly, with every field absent. A hit would then report an untagged album or gain for a file that carries one. So every row carries the archive's format, `VibeMetadataTagsFormat` (`VibeMetadataStore.h`): 12, since the ratings. It was 11, as the PINCache store's last name was `Audio Track Metadata v11`. It was `v8` since the fields, `v9` since the thumbnail left the entry, `v10` since the comment, the grouping, the label, and the bit depth, and `v11` since the extra tags. Bump the number with a change to the archived fields or their meaning. An older row then misses for a read that may open the file, which parses it once and replaces the row. A read that may not, as for a file in the cloud, keeps its answer, marked older (The store, below). So a bump costs one parse of each file the user can read, as the store's rename did, and a file in the cloud keeps its tags and its art.

**Album grouping is `AlbumGroupingRules.h`.** `VibeAlbumGroupKey` gives the key that every track of one album shares. The release identifier is the whole key where present. Otherwise the key is the album artist, the album, and the year. The track artist stands in for a missing album artist. A compilation never splits by track artist. A track without an album has no key. Text compares as tagged. The rule reads values, so an app passes the fields of whatever record it keeps.

## Embedded artwork

`AudioTrackMetadata.h` is the only display API and states each call's contract. `cachedArt` and `cachedThumbnail` never block and are safe while drawing. A cache miss never decodes from a drawing path.

**Across all rows, at most two art reads or decodes run and five wait** (`ArtworkLoadRegistry.h`). A request past the bound is dropped *before* it marks the row pending, so the next redraw re-requests it (spec J6). Only a source-file extraction asks for `MetadataPriority` materialization. A remote placeholder's art is read by range as its tags are (`beginRequest:`), or a lost rendition would download the whole song to show its picture. It still waits out a foreground transfer, as the scan does. An in-memory decode or the folder fallback uses worker admission without materializing the song. `Yielded`, `AdmissionExhausted` and worker rejection retry at a capped 0.1–1 s backoff without spending the three-failure budget. `Failed` spends it. A generation captured at admission must still match before a worker claims extraction or stores its result.

**Parsed metadata is compacted before publication.** A successful 128px thumbnail encode lets the row release its original art bytes. If encoding fails, a fresh row retains the originals until demotion. Decoded thumbnails live in one 16,384-entry LRU (`EmbeddedThumbnailCache`), flushed on an iOS memory warning, with each entry removed when its row's artwork deallocates. **TRAP: the LRU's dictionary is the sole owner of its nodes, and their links are unowned.** Every removal unlinks the node first, in the same critical section. An eviction holds the node's key in a strong local, since the dictionary and the node may hold its only references. Only the display path populates it, so a playlist-wide scan cannot evict visible pixels. A miss enters a two-running, 126-pending decode bound. A main-thread notification, `AudioTrackMetadataThumbnailDidLoadNotification`, then lets an app redraw only the visible rows still showing that metadata. **Staleness has one fence**: every data change replaces the row's identity key and clears its pending flag, so a decode is current exactly when its captured key is still installed. Full art decodes on demand at no more than 1024px. Which surfaces draw the thumbnail is the app's choice. Vibe keeps it for list rows (Vibe's root `AGENTS.md`).

**Compaction also archives a display-art rendition.** It goes in the store as a part of the file's picture, beside its thumbnail (The store, below). `kVibeArchivedDisplayArtDimension` (`core/Graphics`) is 640 on the mac and 1024 on iOS. The iOS size is the size of the live decode it stands in for. Bytes within the bound are archived verbatim. Larger art is downscaled with its aspect kept, since the square crop is display-time policy and Now Playing gets uncropped art. **Files that embed one picture share its archived forms** (`ArchivedArtShare`), as an album's tracks embed one cover. A parse makes the thumbnail and the rendition once while the picture's bytes recur, so a scan decodes each cover once, not once a track. The same SHA-256 names the picture in the disk cache (`VibeArchivedArtOfPictureWithDigest`), so the disk keeps each cover once too. It keeps the last 16 pictures by a SHA-256 of their bytes, and empties 30 s after its last use, so it holds nothing at rest. iOS empties it on a memory warning too. A parse that meets a picture another parse is making waits for it. A picture that won't decode shares no thumbnail, so each row's own decode marks it undecodable. **The rendition lives only on disk: rows never retain it.** The parse hands it to the loader as an out-param. The row retains only the thumbnail after successful compaction.

**The rendition is the big surfaces' decode source.** The loader sets `archivedDisplayArtProvider` on art-bearing cache hits and successful cache writes on both platforms. The full-art ladder reads decoded art, then in-memory bytes, then the archived rendition, then source-file extraction. A usable rendition supplies art without materializing or rereading the song. A provider whose read is empty or undecodable is dropped, and the load takes the demotion fence. `finishRequest` then re-requests a still-wanted row, which reaches extraction. It never sets `_embeddedUndecodable`, since the file's own art may be fine.

**Embedded extraction is tri-state: art, conclusively none, or read failed.** Conclusive absence or an image decode failure enables the folder fallback. A failed read stays unknown and retryable: three reads per display pass, with a two-second per-row backoff. `hasEmbeddedArt` is archived in the entry, and the thumbnail bytes in the picture, so an entry whose thumbnail is gone is not mistaken for artless. Its row thumbnail then decodes from the rendition when one is available.

**An app may guard each read and decode of a file's own art.** A full-art load runs, inside the handler `setEmbeddedArtReadHandler:` sets once a process, on the load's worker: a source-file extraction and its decode, the archived rendition's read and decode, since a rendition within its bound is the file's own bytes, and the decode of bytes a parse kept. Art already decoded reaches no handler, so a load that decodes nothing new costs nothing more. The handler calls `read` at most once, before it returns, since its results live in the load's frame. A handler that never calls it skips the file: `_embeddedReadSkipped` keeps the row from loading again, settles nothing about the file, and opens no folder cover, since the file may carry art. An app guards a file whose art crashes a read this way, as FolderScan's sheet handler guards a sheet's.

**No artwork monitor is held across file I/O or image decoding**, since a provider read can block indefinitely. An entered TagLib read cannot be cancelled and keeps its scheduler slot to completion. Demotion (`discardDecodedArt`) fences its store and re-enters admission if the row is wanted again. **TRAP:** demotion leaves the in-flight extraction claim set, or the next pass could start a second uncancellable read (`AudioTrackArtwork.m`).

## The store

**The disk cache is one `files/DiskCache` `VibeCacheStore`, in a folder named `Audio Track Metadata` under the cache's root** (`VibeMetadataStore`, CH12). A file's entry holds its archived `AudioTrackMetadata`, the tags, the facts, and whether the file carries art, keyed by its `cacheKey` as before (CH9). It names its picture by the lowercase hex SHA-256 of the picture's bytes, which the parse computes already (CH8). A picture is a shared item with two parts: `thumbnail`, the 128 px row thumbnail's encoded bytes, and `rendition` (Embedded artwork, above). So the twelve tracks of an album keep one thumbnail and one rendition. A thumbnail of about 9 KB stays in its row. A rendition over the store's inline limit, 64 KiB, goes to a file the database lists, as most do (CH13). Files/DiskCache's AGENTS.md says how the store keeps them.

**One store per directory a process.** A store opens once (CH21), and Vibe's iOS app keeps two metadata caches over one root. So `VibeMetadataStore` keeps a table of the stores open in the process, by directory. Each cache checks its store out when it opens it, and checks it in at its dealloc. The last check-in closes it. A store that would not open, as when another process holds it, leaves the cache with no store: every read misses, and every write is dropped.

**A hit reads only the tags.** The loader stamps two providers on an art-bearing hit, each a blocking read of one part of the picture the entry names: `archivedThumbnailProvider` and `archivedDisplayArtProvider`. A row's thumbnail decode reads the thumbnail, and falls back to the rendition when that part is gone or will not decode. A provider that read nothing is dropped. An entry that names no picture gets neither. A fresh parse's row holds its thumbnail bytes, and needs neither. An archive that won't decode to `AudioTrackMetadata` is removed. The archive is PINDiskCache's own, an insecure keyed archive, so the import copies the old bytes as they are. Hence the class test.

**A write files the entry, then each part the picture lacks**, then rechecks the generation, as the tag write always has. A part another file of the picture filed already is not written again. A thumbnail or a rendition with no digest, from a parse a test stands in for, is named by its own bytes' digest. An invalidation empties the store. `diskUsageWithCompletion:` reads the store's sums: the entries and the parts, and their bytes. They count the blobs and files, not SQLite's pages, and not the old stores an import has not reached.

**A picture goes when no entry names it, or when a trim takes it** (CH11). The store's triggers remove it with the last entry that names it, or when that entry names another. A trim removes the least recently used rows, entries and parts together, and an entry whose part is gone then reads as art that is not cached, as an evicted thumbnail read before.

**Limits.** An app sets each of the three budgets with `setByteLimit:ageLimit:forStore:`, which runs on the cache's queue once the store is open. **Art never pushes tags out** (CH7, and another app's own call before it). The tags and the thumbnails share the store's byte limit, their two budgets summed, since the store keeps them in rows it does not tell apart. The renditions have a limit of their own (`files/DiskCache`'s `setByteLimit:ofSharedPart:`): their trim takes only renditions, least recently used first, and their bytes never count against the tags. Every row ages by the longest age limit. A tags or thumbnails budget of 0 is none, so it lifts their shared limit. An app that sets nothing gets 2 GiB for the tags and thumbnails, 1 GiB for the renditions, and 180 days from an entry's last use.

**Formats** (CH15 to CH17). Every row carries its format, so a format change never renames the store or removes an entry. The sweep's and the priority lane's reads, and a read by URL that may parse, take only the current format. An older row is a miss, the file is parsed, and the row is replaced. `loadCachedMetadata:`, a `CacheOnly` read, and a `Local` read of a placeholder may not open the file, so an older row answers. Its metadata says `olderFormat`, and the read's result says `older`. Such an answer names no version: its `cacheKey` is nil, so an app's holder takes the next answer in its place, as for a new version, and the sweep and `loadMetadataNow:` treat it as unparsed. A caller that ignores the mark sees the tags as before, with the fields the older format lacks as untagged.

**The import** (CH19, `VibeMetadataImport`). The PINCache stores of the releases before, `Audio Track Metadata v11`, `Audio Track Thumbnails v1`, and `Audio Track Display Art v1`, are read where they are, with no PINDiskCache, so their count at launch never runs. Ten seconds after the store opens, a background queue lists the tag store's folder, and brings over each entry the new store lacks, with its thumbnail and rendition named by the rendition's digest, or the thumbnail's with none. A rendition is the picture's bytes or a fixed downscale of them, so the files of one cover share a name, though not the name a parse gives, which hashes the original. At the end it removes the three folders. From the open on, a miss looks in the old stores before it parses, and a retag's move brings its old entry over first. So the change costs no parse, and a cloud song keeps its art. An import cut short by a quit goes on at the next open, past the entries it brought over. A Clear stops it and removes the old stores. `cacheNames` lists them, so an app's launch removal keeps them until the import removes them, and `files/DiskCache`'s removal keeps every listed name, though two share a family.

**A miss looks once under the file's previous key** (CH33, `core/Common`'s key place). The loader's read and a read by URL pass the file's URL to the store's read (`tagsHitForKey:url:acceptingOlder:`), which asks `previousCacheKeyForKey:` of it on a miss, and moves the entry it finds there, or in the old stores during the import, to the key, with the picture it names. So no file is parsed again for the key's change. It looks while an entry may be under a previous key: during the import, whose entries keep the old stores' keys, and until such an entry would have aged out, as the store's mark says (`files/DiskCache`). The import renews the mark when it ends with entries brought over, and removes each entry's old files once it files them, so a later import never brings back one a miss moved. A move after a tag edit finds the old version under its previous key too, since the app made the old key just before its write. A miss inside the days costs 13 µs median, against 5 µs. After them it costs nothing more, and a hit and a first hit from the disk cost what they did.

**A tag-only rewrite drops the tags and keeps the art** (`moveEntriesOfRetaggedFileFromKey:toKey:artChanged:completion:`, CH10). A tag edit's safe write swaps a rewritten copy in for the file, so its size and date change, and so its key, though its audio is the same. The app takes the file's `cacheKey` before the write and after it, and calls the verb. The entry moves to the new key as a row that names the same picture and holds no tags, of a format no read takes, so the next read parses the new tags and files them, and finds the picture's parts there. No art moves or is written. When the app says the art changed, the entry goes, and its picture with it if no other entry names it. An entry the new key already holds is kept and the old one goes, and an absent entry is no work. It runs on the cache's queue, behind any invalidation. A parse of the old version that ends after it fails its version check, or files under a key no stat gives again. **TRAP: equal keys, from a writer that kept the size and the date, bump the generation.** The key then names the new tags too, so a parse begun before the write would file the old ones under it for good. A row that still holds the old metadata keeps its art providers, which read the picture by its name, so they still draw.

**Measured** on 2026-11-19 on an M4 Max, at a load of 8 to 24 from other work, with one tool built with `-O2`: the three PINCache stores as this cache used them, beside `VibeMetadataStore`, each holding 200,000 tag entries of a 1.0 KB archive, 6,000 of them with art, twelve files to a picture. Three runs each.

| Measure | PINCache, three stores | One store |
| --- | --- | --- |
| A hit, the tags decoded | 37 to 127 µs median | 18 to 20 µs median |
| A row's thumbnail read | 27 to 126 µs median | 6 µs median |
| A miss | 6 µs | 5 µs |

The tool can't drop the file system's own directory cache, so PINCache's numbers are its best case. Before the store keyed its rows by the key's hash, a lookup read the key's index and then the table, and the run took 139 to 179 ms at 284 to 320 µs a hit. The 16 KB pages are filled about 83% when keys arrive in no order, and a vacuumed copy is 223 MB. **The import** brought 200,000 entries over in 326 s, in the background.

**TRAP: the verb retires no memoized key.** `NSURL invalidateMemoizedCacheKeys` is process-wide, so the app calls it once per batch: after its writes, and after every cache's moves have landed, from the last completion. A held row's next lookup then stats the file. Retiring per file would make every held row stat again once a file.

## Folder art

The cover fallback, in `Artwork/FolderArt/`. `FolderArtResolver` is discovery and the two image caches. `FolderArtEntry` is everything known about one directory, mutated only under the resolver's lock. `FolderArtFileIO` probes and reads a candidate with POSIX calls. `FolderArtRules.h` is what a cover may be called. An app also ranks its folder walk's files with it, through the walk's handler for each file it sees. **Embedded art beats a cover.** A cover is resolved lazily per directory, never persisted, and never probed without an active grant. Vibe states this as a guarantee in its root `AGENTS.md`. This is its implementation.

**It is consulted when embedded art is absent or undecodable, and only on macOS.** A failed extraction stays unknown and does not enable the fallback. The resolver builds for both platforms, but `AudioTrackArtwork` leaves its `folderArt` handle nil on iOS.

**Discovery pays for no listing of its own.** A folder open donates the listing the app's walk already made (`noteListedDirectories:…`), so every walked directory settles with no I/O. The walk keeps each directory's best-ranked file by the cover rank the app installs, and it names no cover rule itself. A multi-file open marks its directories for one lazy listing each (`preferListingForDirectories:`). A lone file probes only the three commonest lowercase names (`kVibeFolderArtStatProbeCount`). Every other spelling in `FolderArtRules.h` is matched only against a listing. Settling records a path and opens nothing. The file is read only when a track needs pixels. A row request decodes the thumbnail alone. A display request also fills a missing thumbnail from the same read.

**No active sandbox grant means no probe and no read**, or background work raises a permission panel. An unresolved folder settles "without grant". A known cover whose scope ended keeps its donated path and parks reads until a grant change (`readBlockedWithoutGrant`).

**The lock covers `_directories` and nothing else, and is never held across a stat, read or decode.** Main takes it on every cell draw, and a cover on a sleeping disk or a dataless placeholder blocks for seconds. Drawing paths read cached images or schedule a resolve. Above 4,096 directories, trimming aims for 3,072. In-flight (`busy`) entries are never evicted and may keep the count above that target. Decoded pixels live in `NSCache`: 64 thumbnails and four display images. A cover that exists but fails to read three times settles as none.

**An app may hold covers in the cloud: `holdsCloudCovers`, off by default.** Off, a read of a cover in the cloud downloads it, as any read does. On, a cover the provider holds as a placeholder, by `PlaceholderFiles`' dataless test, is not read. That test catches a remote placeholder too, which the thread's policy doesn't stop. The read itself runs with materialization off for its thread (`VibeWithoutMaterializing`), as the parse's does, so a cover freed after the test fails its read, and the test after it finds it in the cloud. Either way the folder keeps the cover's path, marks it in the cloud (`inCloud`), holds its reads (`readsHeld`), and spends no try. It posts `FolderArtInCloudNotification` once, with the path and the folder, so the app can download the cover under its own rules. `cloudArtPathForAudioFilePath:` reads the path later. `artDidArriveInDirectories:` re-arms the folders and reads each again at once, so its pixels post `FolderArtDidResolveNotification`. A new answer for the folder, from a listing, a settle, or an invalidate, clears the mark, as it clears `readBlockedWithoutGrant`. Its tests stand in for the dataless test through `PlaceholderFiles`' dataless probe.

**`FolderArtDidResolveNotification` fires for "none" as well as a cover**, because an app may keep the previous track's art up while the answer is pending. An app may coalesce it.

**TRAP: `O_NONBLOCK` belongs on the cover file's `open` and nowhere else** (`FolderArtFileIO.m`). It keeps a FIFO or device named `cover.jpg` from wedging the open, since `S_ISREG` is known only after it. Left on across the reads, a file whose bytes are not resident answers `EAGAIN`, which says nothing about the image.

**TRAP: neither normal invalidation is a full wipe.** `folderArtSettingDidChange` drops the decoded images and keeps every settled answer. The setting governs whether the fallback is consulted, not what a folder contains, and a wipe would demote donated covers to the three probes. `invalidateDirectoriesSettledWithoutGrant` forgets only no-grant answers and re-arms read-blocked paths. Opening a folder adds its grant milliseconds later, so a wipe would discard the covers that same open harvested. `invalidate` is test-only.

**The resolver reads no setting and no grant.** The app answers both through `setEnabledProvider:accessProvider:` (the plan's cut 4). Until it does, folder art is off and any directory may be read. An app installs both at launch, from its own setting and its folder grants.

**An app may guard each decode of a cover.** Every decode of a cover's bytes, the row's thumbnail and the display size alike, runs inside the handler `setDecodeHandler:` sets, on the caller's queue, which is never main. The handler calls `decode` at most once, before it returns. A handler that never calls it skips the cover, and the folder counts as having none, as for bytes that don't decode. An app guards a cover that crashes the image decoder this way, as it guards a file's own art.

**TRAP: the resolver caches the app's enabled answer.** Only init, `setEnabledProvider:accessProvider:`, `folderArtSettingDidChange` and the test-only `invalidate` refresh the cached value. So an app calls `folderArtSettingDidChange` after every write of its setting. A write the app does not route there is never observed.

## Tests

`Tests/media/Metadata/` holds the tests of the pipeline. `MetadataTests` runs them on macOS, with the headermap off. It defines `DEBUG` in every configuration, since the loader tests drive the loader's seam and `files/FileLoading`'s.

- **The loader is tested as itself.** The loader tests run the production queues, barrier, ranking, materialization slots, real coordinator, parse claims, installation, publication and cancellation. They replace only cache reads, file parsing and the coordinator's provider-operation boundary. Their harness is `AudioTrackMetadataLoaderTestCase`, which runs no tests, and each topic is a subclass: `AudioTrackMetadataLoaderTests` (stage one, the cache and priority), `…SharedFileTests` (rows that share one file) and `…RetryTests` (retries, the foreground yield, admission, cancellation, and a parse of another version). Their fakes are `MetadataLoaderTestFakes`: `VibeLoaderTestTrack`, the tests' own holder, which memoizes its key as an app's item may, a duck-typed metadata, the loader's owner and delegate, and a provider operation each test completes by hand. Do not copy the loader's state machine into a fake or flatten it into rule tests.
- `AudioTrackMetadataReadingTests` runs the reads by URL over a store of its own, with the real parse, and counts, holds, or stands in for a parse through the cache's `debugSetReadingFileParser:`. A placeholder is `PlaceholderFiles`' dataless probe. `AudioTrackMetadataCacheTests` runs the cache itself over a store of its own, and holds the store's open at a gate. A load issued before the store exists is delivered and filed, and a second cache over the same root hits. It also checks that the store's names follow `files/DiskCache`'s version rule, and that a store before v11 is never read. It checks that art is filed under its picture, that two files with one picture keep one thumbnail and one rendition, and that a picture goes with the last entry that names it. It checks the budgets' sum. It rewrites a file as a tag edit's safe write does, and checks the move: the entry names the same picture and no art is written, the tags are parsed again, changed art is dropped, an absent entry moves nothing, an entry under the new key outlives the move, and equal keys keep a parse in flight from filing. Its format and import tests are below. `MetadataParseCoordinatorTests`, `MetadataRetryRulesTests`, `MetadataScanOrderRulesTests`, and `AlbumGroupingRulesTests` cover the claim table and the rules. The grouping has a case for each rule above. `Artwork/` covers the artwork's state and loads, the thumbnail cache, and the folder art resolver and its rules.
- **The previous keys' tests.** An entry under a file's previous key moves to its key with its picture, and no parse runs. After the age limit, a miss parses. A tag edit's move finds the old version under its previous key, and keeps the art. The old stores the import tests fill are keyed by previous keys, as the releases before keyed them.
- **The cache's format and import tests.** The format tests write an older row: a read that may parse misses it, a cache-only read answers it marked older, and a holder takes the next parse in its place. The import tests fill the PINCache stores as their cache did, through `Tests/Support/LegacyCacheFixtures.h`, since PINCache is gone: every entry reads back the same, a miss before the import finds the old entry with no parse, an import cut short goes on at the next open, a Clear removes the old stores, and the old stores are gone at the end.
- **The tag parse runs over the real TagLib.** `AudioTrackMetadataTagTests` runs `metadataWithURL:displayArtData:` and the art read over each format: ID3v2.3, ID3v2.4, ID3v1 and APE on MP3, Monkey's Audio with an APEv2 tag, M4A, FLAC with a picture and with a CUESHEET block, Vorbis, Opus, WAV with ID3 or RIFF INFO, AIFF, CAF and W64. It checks tags, tempo and key, codec facts and the bit depth, every tag field each format carries, the grouping's and the label's other keys, FLAC's audio MD5, art that will not decode, art whose header claims a huge image, a file whose extension misleads, and a remote placeholder's tags and art through its backend's read. Each fixture carries every tag field its format does, and the fields survive the cache's archive and a copy. Each field also gets a test of its own, which writes that field alone in each format that carries it. `AudioTrackMetadataFuzzTests` mutates those files with a fixed seed. Each mutant must parse or fail within a bound and throw nothing. `TEST_RUNNER_VIBE_FUZZ_ROUNDS` raises the rounds, and `TEST_RUNNER_VIBE_FUZZ_SEED` changes the seed. Both write their files with `AudioTrackMetadataTagFixtures.h`: audio from `Tests/Support`'s `AudioFileFixtures.h` or an Apple encoder, then tags from TagLib's own writers. The art is `ImageFixtures.h`'s.

**Ogg's audio comes from an app's generated fixtures**, which these tests find where `VIBE_AUDIO_FIXTURES` points. Nothing here generates them, so the Vorbis and Opus cases skip here. FLAC's Xiph comment still covers every Xiph field here, R128's gains included. Vibe's `VibeAudioTests` compiles the tag and fuzz tests from the submodule (`make test-audio`), over the fixtures it generates, so those cases run there. Vibe keeps its row's tests over the real parse, and its test of the walk's handoff to the resolver.

**A bounded wait is a hang guard or a gate.** A wait for what must happen uses `VIBE_TEST_HANG_TIMEOUT`. A gate the test releases itself uses `VIBE_TEST_GATE_TIMEOUT`. A negative check uses `kVibeTestNegativeWindow` (`Tests/Support`). The bundle defines both bounds. Run the fuzz with a raised count under `-enableAddressSanitizer YES -enableUndefinedBehaviorSanitizer YES` after a change to the parse.

The minimal consumer roots a metadata cache of its own, tags a WAV with a title, an album, and a picture through TagLib, and loads it through the cache with a holder of its own, at once after init. It reads the title, the album, and the picture's bytes back, groups the album, and waits for the row thumbnail. A second cache over the same root then loads a fresh row with `loadCachedMetadata:`, and the hit gives the same title and album.

`Tests/Fuzz/` also fuzzes this piece by coverage, under sanitizers, through its `tags-*` targets ([Tests/Fuzz/AGENTS.md](../../Tests/Fuzz/AGENTS.md)).
