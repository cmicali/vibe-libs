# media/Metadata

The tag record and its CoreAudio fallback, the disk cache of tags, the background scan, embedded art and the shared row thumbnails, and covers beside the files. **Today it holds Vibe's metadata pipeline, moved from Vibe** with the cache's and the loader's debug seams. It depends on `core/Common`, `audio/AudioTypes` for the playable item and the format names, `audio/Decode` for the fallback's handle, `media/Tags` for the TagLib parse, `files/DiskCache` for the store, `files/FileLoading` for the materialization and the ranged read, `core/Graphics` for the image helpers, and `third_party/taglib` and `third_party/PINCache`, whose own headers the parse and the cache read. It reads no app's settings, strings, or types. It builds on both platforms, and no file needs a platform half.

**What an app gives it.** Its items, any object adopting `AudioTrackMetadataHolder` (below). A cache root, or nil for the user's Caches directory. Folder art's two answers, its switch and its access check, as blocks (Folder art, below). The tracks near the one playing, as they change. How Vibe's shells drive it, and the guarantees Vibe states over it, are Vibe's `Audio/AGENTS.md`.

**Artwork is the one place it hands out UI types.** It returns `NSImage` on macOS and `UIImage` on iOS, through `core/Graphics`' `VibeImage`.

## Files

- `AudioTrackMetadataCache` is the facade, and `AudioTrackMetadataLoader` the one sweep behind it (private). Its disk cache sits under the root `initWithRootPath:` names. Nil, which `init` passes, is the user's Caches directory.
- The loader is one object in three files. `AudioTrackMetadataLoader.m` is its life and the sweep's stage 1. `+Materialization.m` is the lane: priority marks, the two slots, the foreground gate and each completion's settlement. `+Parse.m` is the cache read, the parse, installation, settlement and publication, with the display-art rendition's sidecar. `AudioTrackMetadataLoader.h` is the API the cache and the tests use. `AudioTrackMetadataLoaderInternal.h` holds its ivars and the methods its files share. `MetadataScanEntry` holds its two records, the scan entry and the priority mark. Its debug seam is `AudioTrackMetadataLoader+Debug`, beside it, and the cache's is `AudioTrackMetadataCache+Debug`. Each header declares its surface in every build, and each implementation wraps its body in `#if DEBUG`.
- `AudioTrackMetadataHolder` is what the loader takes of an item. It extends `VibePlayableItem` with the installed metadata, the install that happens only while the item has no answer from the same version, and the delivery that runs only while that answer is still installed. The holder keeps the check and the store under its own monitor, which must be recursive. It is this piece's own protocol (the plan's seam 22), so the playable item stays free of metadata.
- `MetadataParseCoordinator` is the per-path owner/waiter table and nothing else.
- `AudioTrackMetadata` is the immutable tags plus the display-facing art API. `AudioTrackMetadataInternal.h` is the loader's construction surface: the parse, the artwork, and the version stamp.
- The TagLib side of the parse is `media/Tags`: `TagLibAudioFile`, the file factory, the ranged stream, the format name and the embedded art's bytes. It reads from disk, or through a byte-range reader the caller passes. `AudioTrackMetadata.mm` chooses the reader and turns the art read into the artwork's extractor (`VibeTagLibArtExtractor`). The parse reads the tags from TagLib's own types, which the map allows. The title and the artist come from the tag, and every other field from one property map (The tag fields, below). The wrapper answers what no tag holds: the format, the art, and FLAC's audio MD5. The wrapper's header is C++, so only `.mm` files import it. `NSString+CPPStrings` turns TagLib's UTF-8 into a string, embedded NULs kept.
- `AudioTrackArtwork` is one row's art lifecycle (private behind the metadata). `ArtworkLoadRegistry` is its admission counters, a file boundary, not a second owner.
- `AudioTrackArtwork` is one object in two files. `AudioTrackArtwork.m` is the art state, adoption, the archived display art, demotion and the row thumbnails. `+Loading.m` is the full-art load: the extraction gate, the blocking read ladder and the async load the registry admits. `AudioTrackArtworkInternal.h` holds the ivars and the methods both files share.
- `EmbeddedThumbnailCache` is the decoded thumbnails every row shares, in one bounded LRU.
- `NSURL+FilenameTitle` is the title a file's name gives, which a parse without a tagged title keeps.
- `AlbumGroupingRules.h` is which album a track belongs to (The tag fields, below).
- `Artwork/FolderArt/` is the cover fallback (Folder art, below).

**Do not add a runner, driver or second coordinator.** Straight-line metadata work goes in the loader, per-row art work in `AudioTrackArtwork`. The lettered items the comments cite (`spec A1`, `J4`, `J6`) are Vibe's `docs/file-loading-spec.md`'s.

## The scan

**A metadata request may start before a file is materialized. A TagLib parse may not.** The disk-cache check never reads audio, so known rows populate without touching their files. On a miss, `AudioFileMaterializationCoordinator` must report `Ready` before the parse enters a worker.

**The one exception is a remote placeholder of a format TagLib parses.** The rule is `PlaceholderFiles readsRemotePlaceholderByRange:`, over `PlayableExtensions.tagParsed`, and the art loader shares it. Other formats take CoreAudio's facts, which need the whole file, so they materialize. The scan settles such a placeholder Ready with no claim (`submitMaterializationForEntry:`). `AudioTrackMetadata.mm` passes the backend's read (`remoteReadForURL:`) to `TagLibAudioFile`. The wrapper reads through it in blocks, following the parser's reads, artwork included (`media/Tags/AGENTS.md`). A file the backend is streaming is read from the stream, at no request cost. A server that ignores the range sends from the start. The client skips to the requested offset and cancels once it has the requested bytes. A tail read can therefore transfer most of the song. It takes no claim because stage 1 is one claim per path shared by every role. A metadata Ready on a placeholder would hand a playback open joining that claim an unreadable file. It is still a network read, so the foreground rule below gates it.

**The playlist sweep has two stages, and only stage 2 can download.** Stage 1 checks every file against the cache once, behind an operation-queue barrier that waits for enumeration and every check. Stage 2 admits the misses. **A record is a file, not a row.** The rows sharing a standardized path (a cue sheet's forty, a file listed twice) are one record: checked, materialized and parsed once, with its answer copied to every row. A failed parse gives its fallback to the row it read for (the marked row when there is one) and requeues the rest as a record of their own. The scan registers exactly one `MetadataScan` materialization at a time.

**The current track is not a second lane. It is the record holding a row the loader has marked.** It materializes through its own slot beside the scan's, skips the stage-1 barrier, and is submitted even under the foreground rule, since a same-path playback claim serves it for free (spec J4). It parses at user-initiated QoS. Demotion removes the mark, and so does removing the marked row (`abandonQueuedTrack:`), since a marked URL holds its file's other records out of the scan. Every mark carries a generation and its exact target track, and settlement retires only a mark it resolved. A repeat edge reactivates one submission so it can join a new same-path foreground claim. Both slots spend the one per-path retry ledger. A `loadMetadataNow:` before any sweep builds a loader over that one track. The real sweep replaces it and re-prioritizes the weakly held current track. `cancelScan` drops every pending record, priority included, so replacing the playlist drops the old playlist's downloads. It detaches central tokens without cancelling a same-path foreground owner.

**`loadCachedMetadata:` is the cache check alone**, for rows whose audio is not on the device, such as a file browser's placeholders and dataless files. A hit installs and publishes as the sweep's does. A miss ends there, with no record, materialization or parse (`loadFromCacheOnly:`). It runs on a loader of its own that is never cancelled, so a later `loadMetadata:` or `cancelScan` cannot drop a lookup the caller will not repeat.

**The foreground rule is the coordinator's. This piece only asks** (`files/FileLoading/AGENTS.md`). The sweep asks `isForegroundTransferActive` before submitting a dataless record, and re-asks on a bounded 1 s clock while gated (`recheckForegroundGate`, the seam the tests drive). Cache checks continue while gated. **An already-local file is exempt**, so on a partly downloaded folder local tags land straight through. The loader probes locality with `PlaceholderFiles.isDatalessFile:` at every enqueue, submit and requeue, because the playback open routinely downloads the very file a yielded record waits on.

**Materialization results, not error text, decide retries** (`MetadataRetryRules.h`, tested):

- `Yielded` spends no attempt, and a scan record requeues at its rank. A yielded **priority** record is re-judged on each gated tick. Local now, it retries at once (spec A1), since waiting cost the now-playing tags the successor's whole prefetch. Still dataless, it waits rather than re-pick, since a re-pick installs a fresh `Probing` claim and yields again. At the **first idle tick**, still dataless means the open failed, so it demotes to an ordinary sweep candidate.
- `Failed` spends the bounded per-path budget and re-enters below untried rows. `AdmissionExhausted` spends the same budget after a 0.25–2 s delay.

A loader snapshots `AudioLoadingConfiguration`, so a settings change reaches only later loaders.

**Pending misses are records picked one at a time, never sorted** (`MetadataScanOrderRules.h`, tested): already-local first, then untried before deferred, then neighborhood rank, then playlist index. A real playlist holds more than 100,000 misses, so a track change replaces only a small locked neighborhood snapshot and enqueues a coalesced kick. An app sends the snapshot through `setNeighborhoodTracks:` when its current track changes. It hands over the next few tracks in play order, so shuffle ranks what will play, never the whole list.

**The cache key is the item's `cacheKey` (`VibePlayableItem`).** An item may memoize it until a download installs another version than its placeholder's (`files/FileLoading/AGENTS.md`). Then every memo is retired and the next lookup stats the file again. Each installed metadata carries the key it was read under (`AudioTrackMetadata.cacheKey`). A row whose key no longer matches it is parsed again in the next sweep, and the new version's answer replaces the old one. A priority edge does not check the version, because it runs on main and must not stat.

**A load never runs ahead of the store.** The cache builds its PINCache on its own utility queue after init, since building it on main lifts PINCache's start-up disk scan to main's QoS. A read of the store before it exists waits for the build, through `dispatch_sync` on that queue, which lends the reader's QoS to the build (`metadataCache`). So a load issued at once after init is looked up and filed like any other. There is no "ready" signal, because no caller can race the store. A waiter would grow the API, and every caller would have to remember it. Only a read that races the build waits, and only once. The waiting reads are the loader's workers. Main never reads the store, so `loadCachedMetadata:` enqueues its lookups straight from main.

**TRAP: a parse's version is checked at its completion, never at its start.** The key is taken before the read. A placeholder's parse can read from the download that installs another version, and that download re-keys only when it ends. At completion the loader reads the item's `cacheKey` again and compares it with the key the parse was looked up under. On a mismatch the result is neither installed, delivered nor filed, since its bytes may be either version's. The record, with the claim's waiters, parses once more under the new key (`AudioTrackMetadataLoader+Parse.m`). It is not requeued through the lane, because the new version is already on disk and the lane would drop a priority record's mark. The item's key is compared, never a fresh stat, so the next parse is keyed as the check is.

## Duplicate rows and delivery

**One parse per standardized path** (`VibeStandardizedAudioOpenPath`, the spelling every loader identity uses). `MetadataParseCoordinator` holds duplicate rows weakly as waiters. The owner rechecks the disk cache after claiming, since another lane may have won. Its answer is copied into every unresolved waiter while the holder still gates new owners, and the last empty drain releases the claim before publication. Each copy has its own artwork state.

**A file TagLib has no parser for takes its facts from CoreAudio's**: CAF and W64 among the playable ones, and any file TagLib refuses that CoreAudio reads. Those are duration, rate, bitrate, the codec or container name, and the info dictionary's title and artist, with no art. It parses OK, caches, and the folder's cover can stand in (`loadCoreAudioFactsFromURL:`). It reads them through `AudioFileHandle`'s `initParserForReading:`, CoreAudio's parser with no decoder. The verdict is CoreAudio's. Playback opens FLAC, WAV, W64, RF64, AIFF, Ogg Vorbis and MPEG with `audio/Decode`'s own decoders. It can disagree with CoreAudio on those.

**TRAP: a CAF's info chunk is checked before CoreAudio reads it.** CoreAudio's info parser loops without end on a forged entry count, and the hang holds a metadata worker forever. `loadCoreAudioFactsFromURL:` reads the info dictionary only when the handle's `infoDictionaryReadable` says so (`audio/Decode/AGENTS.md`). The format facts still come from CoreAudio.

**The fallback opens never wait for a download or read ahead.** Both pass `VibeNeverWaitsForAStream`: CoreAudio's facts open and dr_flac's FLAC-length open (`AudioFileHandle.h`, compared by identity). Against a file a transfer is still writing, the open fails at once, and the facts come once the file is on disk. On a network share the open reads the file directly, as TagLib's parse does.

**TRAP: the TagLib parse must refuse what that open refuses.** TagLib's FLAC sniff takes FLAC in Ogg, which playback refuses. So the wrapper parses no Ogg stream as FLAC (`media/Tags/TagLibAudioFile.mm`). Such a file is a failed parse, not a row that looks playable.

**A file neither parser reads produces uncached fallback metadata.** An exception after partial parsing can leave some facts installed. Neither fallback nor partial results enter the cache. The holder and every waiter get their own fallback copies, so no row stays unresolved. Installation and publication compare the exact metadata object under the track monitor. A racing success replaces a fallback, and the stale fallback's delivery drops.

**Every delivery runs on main and revalidates the exact installed object while holding the track monitor through the delegate call.** Delegates may update UI synchronously. They must never wait on a metadata worker.

## The tag fields

**The record holds the fields a library app reads.** Beside the title, the artist, the tempo, and the key, it holds the album, the album artist, the genre, the composer, the year, the track and disc numbers and counts, and the compilation flag. It holds MusicBrainz's release and recording identifiers and the ISRC. It holds FLAC's audio MD5. It holds the loudness tags: ReplayGain's track and album gain and peak, Opus's R128 track and album gain, and Apple's Sound Check. A field the file lacks is nil, 0, or NO.

**The parse reads them from the property map it builds once for the tempo and the key.** TagLib turns each format's frame or atom into one key, and its keys ignore case. So one lookup serves every format. These are the names each format's tag carries:

| --- | --- | --- | --- | --- | --- | --- |
| album | `TALB` | `©alb` | `ALBUM` | `Album` | `IPRD` | album |
| album artist | `TPE2` | `aART` | `ALBUMARTIST` | `Album Artist` | | |
| genre | `TCON` | `©gen` or `gnre` | `GENRE` | `Genre` | `IGNR` | genre |
| composer | `TCOM` | `©wrt` | `COMPOSER` | `Composer` | `IMUS` | |
| year | `TDRC`, or v2.3's `TYER` | `©day` | `DATE` | `Year` | `ICRD` | year |
| track number and count | `TRCK` | `trkn` | `TRACKNUMBER`, then `TRACKTOTAL` or `TOTALTRACKS` | `Track` | `IPRT` | track |

Opus defines the R128 gains. The parse reads them from any Xiph comment, since the lookup is the same. A count comes from the number's tag, as in "3/12", or else from a tag of its own. The year is the date's leading number.

**Each gain keeps its own reference level.** A ReplayGain gain is the tagged decibels, toward ReplayGain's reference. An R128 gain is Opus's Q7.8 whole number over 256, toward −23 LUFS, on top of the header's output gain. Sound Check's gain is −10 log10 of the louder of iTunNORM's first two words over 1000. Peaks are linear, with 1 at full scale. An app that levels by them converts between references itself.

**FLAC's audio MD5 comes from STREAMINFO**, through the wrapper's `audioMD5FromTagLibFile`. It is the MD5 of the decoded samples, so a retag never changes it. An encoder that computed none writes zeros, which read as nil.

**CoreAudio's facts carry none of the fields.** A CAF or a W64 reads its title and artist from the info dictionary, and nothing else.

**TRAP: an entry archived before the fields must be a miss.** It decodes cleanly, with every field absent. A hit would then report an untagged album or gain for a file that carries one. So the store's name carries the archive's version, `v8` since the fields (`AudioTrackMetadataCache.m`). The cost is one parse of every file, once. An app ships the bump in a release that announces it.

**Album grouping is `AlbumGroupingRules.h`.** `VibeAlbumGroupKey` gives the key that every track of one album shares. The release identifier is the whole key where present. Otherwise the key is the album artist, the album, and the year. The track artist stands in for a missing album artist. A compilation never splits by track artist. A track without an album has no key. Text compares as tagged. The rule reads values, so an app passes the fields of whatever record it keeps.

## Embedded artwork

`AudioTrackMetadata.h` is the only display API and states each call's contract. `cachedArt` and `cachedThumbnail` never block and are safe while drawing. A cache miss never decodes from a drawing path.

**Across all rows, at most two art reads or decodes run and five wait** (`ArtworkLoadRegistry.h`). A request past the bound is dropped *before* it marks the row pending, so the next redraw re-requests it (spec J6). Only a source-file extraction asks for `MetadataPriority` materialization. A remote placeholder's art is read by range as its tags are (`beginRequest:`), or a lost rendition would download the whole song to show its picture. It still waits out a foreground transfer, as the scan does. An in-memory decode or the folder fallback uses worker admission without materializing the song. `Yielded`, `AdmissionExhausted` and worker rejection retry at a capped 0.1–1 s backoff without spending the three-failure budget. `Failed` spends it. A generation captured at admission must still match before a worker claims extraction or stores its result.

**Parsed metadata is compacted before publication.** A successful 128px thumbnail encode lets the row release its original art bytes. If encoding fails, a fresh row retains the originals until demotion. Decoded thumbnails live in one 16,384-entry LRU (`EmbeddedThumbnailCache`), flushed on an iOS memory warning, with each entry removed when its row's artwork deallocates. Only the display path populates it, so a playlist-wide scan cannot evict visible pixels. A miss enters a two-running, 126-pending decode bound. A main-thread notification, `AudioTrackMetadataThumbnailDidLoadNotification`, then lets an app redraw only the visible rows still showing that metadata. **Staleness has one fence**: every data change replaces the row's identity key and clears its pending flag, so a decode is current exactly when its captured key is still installed. Full art decodes on demand at no more than 1024px. Which surfaces draw the thumbnail is the app's choice. Vibe keeps it for list rows (Vibe's root `AGENTS.md`).

**Compaction also archives a display-art rendition beside the entry.** It has a `#displayArt`-suffixed key in the same store, on the same LRU and age terms. `kVibeArchivedDisplayArtDimension` (`core/Graphics`) is 640 on the mac and 1024 on iOS, the size of the live decode it stands in for. Bytes within the bound are archived verbatim. Larger art is downscaled with its aspect kept, since the square crop is display-time policy and Now Playing gets uncropped art. **The rendition lives only on disk: rows never retain it.** The parse hands it to the loader as an out-param. The row retains only the thumbnail after successful compaction.

**The rendition is the big surfaces' decode source.** The loader sets `archivedDisplayArtProvider` on art-bearing cache hits and successful cache writes on both platforms. The full-art ladder reads decoded art, then in-memory bytes, then the archived rendition, then source-file extraction. A usable rendition supplies art without materializing or rereading the song. A provider whose read is empty or undecodable is dropped, and the load takes the demotion fence. `finishRequest` then re-requests a still-wanted row, which reaches extraction. It never sets `_embeddedUndecodable`, since the file's own art may be fine.

**Embedded extraction is tri-state: art, conclusively none, or read failed.** Conclusive absence or an image decode failure enables the folder fallback. A failed read stays unknown and retryable: three reads per display pass, with a two-second per-row backoff. `hasEmbeddedArt` is archived apart from the thumbnail bytes, so an entry without them is not mistaken for artless. Its row thumbnail can then decode from the rendition when one is available.

**No artwork monitor is held across file I/O or image decoding**, since a provider read can block indefinitely. An entered TagLib read cannot be cancelled and keeps its scheduler slot to completion. Demotion (`discardDecodedArt`) fences its store and re-enters admission if the row is wanted again. **TRAP:** demotion leaves the in-flight extraction claim set, or the next pass could start a second uncancellable read (`AudioTrackArtwork.m`).

## Folder art

The cover fallback, in `Artwork/FolderArt/`. `FolderArtResolver` is discovery and the two image caches. `FolderArtEntry` is everything known about one directory, mutated only under the resolver's lock. `FolderArtFileIO` probes and reads a candidate with POSIX calls. `FolderArtRules.h` is what a cover may be called. An app also ranks its folder walk's files with it, through the walk's handler for each file it sees. **Embedded art beats a cover.** A cover is resolved lazily per directory, never persisted, and never probed without an active grant. Vibe states this as a guarantee in its root `AGENTS.md`. This is its implementation.

**It is consulted when embedded art is absent or undecodable, and only on macOS.** A failed extraction stays unknown and does not enable the fallback. The resolver builds for both platforms, but `AudioTrackArtwork` leaves its `folderArt` handle nil on iOS.

**Discovery pays for no listing of its own.** A folder open donates the listing the app's walk already made (`noteListedDirectories:…`), so every walked directory settles with no I/O. The walk keeps each directory's best-ranked file by the cover rank the app installs, and it names no cover rule itself. A multi-file open marks its directories for one lazy listing each (`preferListingForDirectories:`). A lone file probes only the three commonest lowercase names (`kVibeFolderArtStatProbeCount`). Every other spelling in `FolderArtRules.h` is matched only against a listing. Settling records a path and opens nothing. The file is read only when a track needs pixels. A row request decodes the thumbnail alone. A display request also fills a missing thumbnail from the same read.

**No active sandbox grant means no probe and no read**, or background work raises a permission panel. An unresolved folder settles "without grant". A known cover whose scope ended keeps its donated path and parks reads until a grant change (`readBlockedWithoutGrant`).

**The lock covers `_directories` and nothing else, and is never held across a stat, read or decode.** Main takes it on every cell draw, and a cover on a sleeping disk or a dataless placeholder blocks for seconds. Drawing paths read cached images or schedule a resolve. Above 4,096 directories, trimming aims for 3,072. In-flight (`busy`) entries are never evicted and may keep the count above that target. Decoded pixels live in `NSCache`: 64 thumbnails and four display images. A cover that exists but fails to read three times settles as none.

**`FolderArtDidResolveNotification` fires for "none" as well as a cover**, because an app may keep the previous track's art up while the answer is pending. An app may coalesce it.

**TRAP: `O_NONBLOCK` belongs on the cover file's `open` and nowhere else** (`FolderArtFileIO.m`). It keeps a FIFO or device named `cover.jpg` from wedging the open, since `S_ISREG` is known only after it. Left on across the reads, a file whose bytes are not resident answers `EAGAIN`, which says nothing about the image.

**TRAP: neither normal invalidation is a full wipe.** `folderArtSettingDidChange` drops the decoded images and keeps every settled answer. The setting governs whether the fallback is consulted, not what a folder contains, and a wipe would demote donated covers to the three probes. `invalidateDirectoriesSettledWithoutGrant` forgets only no-grant answers and re-arms read-blocked paths. Opening a folder adds its grant milliseconds later, so a wipe would discard the covers that same open harvested. `invalidate` is test-only.

**The resolver reads no setting and no grant.** The app answers both through `setEnabledProvider:accessProvider:` (the plan's cut 4). Until it does, folder art is off and any directory may be read. An app installs both at launch, from its own setting and its folder grants.

**TRAP: the resolver caches the app's enabled answer.** Only init, `setEnabledProvider:accessProvider:`, `folderArtSettingDidChange` and the test-only `invalidate` refresh the cached value. So an app calls `folderArtSettingDidChange` after every write of its setting. A write the app does not route there is never observed.

## Tests

`Tests/media/Metadata/` holds Vibe's tests of the pipeline. `MetadataTests` runs them on macOS, with the headermap off. It defines `DEBUG` in every configuration, since the loader tests drive the loader's seam and `files/FileLoading`'s.

- **The loader is tested as itself.** The loader tests run the production queues, barrier, ranking, materialization slots, real coordinator, parse claims, installation, publication and cancellation. They replace only cache reads, file parsing and the coordinator's provider-operation boundary. Their harness is `AudioTrackMetadataLoaderTestCase`, which runs no tests, and each topic is a subclass: `AudioTrackMetadataLoaderTests` (stage one, the cache and priority), `…SharedFileTests` (rows that share one file) and `…RetryTests` (retries, the foreground yield, admission, cancellation, and a parse of another version). Their fakes are `MetadataLoaderTestFakes`: `VibeLoaderTestTrack`, the tests' own holder, which memoizes its key as an app's item may, a duck-typed metadata, the loader's owner and delegate, and a provider operation each test completes by hand. Do not copy the loader's state machine into a fake or flatten it into rule tests.
- `AudioTrackMetadataCacheTests` runs the cache itself over a store of its own, and holds the store's build at a gate. A load issued before the store exists is delivered and filed, and a second cache over the same root hits. `MetadataParseCoordinatorTests`, `MetadataRetryRulesTests`, `MetadataScanOrderRulesTests`, and `AlbumGroupingRulesTests` cover the claim table and the rules. The grouping has a case for each rule above. `Artwork/` covers the artwork's state and loads, the thumbnail cache, and the folder art resolver and its rules.
- **The tag parse runs over the real TagLib.** `AudioTrackMetadataTagTests` runs `metadataWithURL:displayArtData:` and the art read over each format: ID3v2.3, ID3v2.4, ID3v1 and APE on MP3, M4A, FLAC with a picture and with a CUESHEET block, Vorbis, Opus, WAV with ID3 or RIFF INFO, AIFF, CAF and W64. It checks tags, tempo and key, codec facts, every tag field each format carries, FLAC's audio MD5, art that will not decode, art whose header claims a huge image, a file whose extension misleads, and a remote placeholder's tags and art through its backend's read. Each fixture carries every tag field its format does, and the fields survive the cache's archive and a copy. Each field also gets a test of its own, which writes that field alone in each format that carries it. `AudioTrackMetadataFuzzTests` mutates those files with a fixed seed. Each mutant must parse or fail within a bound and throw nothing. `TEST_RUNNER_VIBE_FUZZ_ROUNDS` raises the rounds, and `TEST_RUNNER_VIBE_FUZZ_SEED` changes the seed. Both write their files with `AudioTrackMetadataTagFixtures.h`: audio from `Tests/Support`'s `AudioFileFixtures.h` or an Apple encoder, then tags from TagLib's own writers. The art is `ImageFixtures.h`'s.

**Ogg's audio comes from an app's generated fixtures**, which these tests find where `VIBE_AUDIO_FIXTURES` points. Nothing here generates them, so the Vorbis and Opus cases skip here. FLAC's Xiph comment still covers every Xiph field here, R128's gains included. Vibe's `VibeAudioTests` compiles the tag and fuzz tests from the submodule (`make test-audio`), over the fixtures it generates, so those cases run there. Vibe keeps its row's tests over the real parse, and its test of the walk's handoff to the resolver.

**A bounded wait is a hang guard or a gate.** A wait for what must happen uses `VIBE_TEST_HANG_TIMEOUT`. A gate the test releases itself uses `VIBE_TEST_GATE_TIMEOUT`. A negative check uses `kVibeTestNegativeWindow` (`Tests/Support`). The bundle defines both bounds. Run the fuzz with a raised count under `-enableAddressSanitizer YES -enableUndefinedBehaviorSanitizer YES` after a change to the parse.

The minimal consumer roots a metadata cache of its own, tags a WAV with a title, an album, and a picture through TagLib, and loads it through the cache with a holder of its own, at once after init. It reads the title, the album, and the picture's bytes back, groups the album, and waits for the row thumbnail. A second cache over the same root then loads a fresh row with `loadCachedMetadata:`, and the hit gives the same title and album.
